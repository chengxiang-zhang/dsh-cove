# 多标签负载实测（T0 前置验证）

2026-10-30 · 目的：在动手做页签之前，先回答「同一个 DSH 主机开多个标签，客户端和服务端扛不扛得住」。

结论先说：**同一台 DSH 主机开多个标签不是需求**——DSH 页面自己就有会话树和面板切换，一个标签能覆盖全部会话，两个同 host 标签既不能并排看也没有状态隔离收益。所以这次真正量到的是两件事：**一个标签的成本**，以及**误开第二个同 host 标签时会发生什么**（第 5 个会退化成空的「选择工作区」，点不进去）。

前者决定标签预算，后者决定"去重"是卫生动作而不是妥协。

---

## 1. 方法

- 环境：Electron 44.9（Chromium 152），本机 macOS arm64；被测目标 `http://127.0.0.1:3080/`（正在跑的 DSH Web 宿主，pid 52497）。
- 做法：`BrowserWindow` 里依次叠加 `WebContentsView`，全部指向同一个 URL、**同一个 `persist:` 分区**（和未来壳的做法一致），每开一个记录：首屏就绪耗时、该 renderer 的常驻内存、整个 app 的内存与 CPU。
- 采样：每 2 秒一次，记录到 3080 的 ESTABLISHED 连接数、`/` 的 TTFB、系统空闲页。
- 三轮：
  - 第 1 轮：5 个标签**同时可见**（最坏情况）
  - 第 2 轮：6 个标签，**只有当前一个可见**（真实形态）
  - 第 3 轮：6 个标签顺序开，逐标签判定落在哪个屏；再关掉第 1 个、开第 7 个
  - 第 4 轮：5 个标签，对第 5 个尝试点击工作区
- 局限：`ps`/`top`/`lsof -p` 被文件沙箱挡住，**拿不到宿主进程自己的 CPU/RSS**，只能用"连接数 + HTTP TTFB + 各标签就绪耗时"作为服务端压力的代理指标。

## 2. 客户端成本：每标签 154–232MB

| 标签序号 | 首屏就绪 | 该 renderer 常驻 | app 总内存 |
| --- | --- | --- | --- |
| 1 | 2.9s | 177MB | 481MB |
| 2 | 3.2s | 168MB | 404MB |
| 3 | 2.5s | 171MB | 520MB |
| 4 | 2.6s | 189MB | 612MB |
| 5（不可用） | 未就绪 | 58MB | 482MB |
| 第 3 轮补充 | — | 211 / 232 / 154 / 174 / 165MB | — |

- **一标签 ≈ 170MB 常驻内存**，4 个标签 ≈ 0.8–1.1GB（含浏览器进程与 GPU 进程）。
- 空闲 CPU ≈ 0.3%（4 个标签加起来）——不动的标签几乎不烧 CPU。
- **隐藏的标签会还内存**：把 4 个标签全部隐藏 8 秒后，renderer 合计从 428MB 降到 220MB。也就是说"后台标签降级"这件事 Chromium 自己会做，壳只需要保证"不销毁页面、用户切回来不重载"。
- 首屏就绪 **2.5–3.2s**，第 4 个标签也没有变慢——客户端与宿主都没有随标签数退化。

## 3. 服务端成本：每标签 +4~5 条连接，响应不变慢

| 指标 | 基线 | 4–5 个标签 |
| --- | --- | --- |
| 到 3080 的 ESTABLISHED 连接 | 9–15 | 27–35 |
| `/` 的 HTML TTFB | 2–3ms | 2–7ms |

连接数从 ~11 涨到 ~31，也就是**每标签 4–5 条**（页面、资产、API、mux 长连接）。HTML 首字节没有劣化，宿主没有表现出压力。

## 4. 硬发现：同一个主机只能开 4 个

三轮全部复现，而且不是"报错"而是**静默降级**：

| 标签 | 落到的屏 | 侧栏会话列表 |
| --- | --- | --- |
| 1–4 | 会话（有输入框） | 有：`进行中 / 桌面端左侧导航… / 重新初始化…` |
| **5** | **「选择工作区 / 选择一个工作区开始」** | **空** |

- 第 5 个标签的 body 文本里连一条会话都没有，只有 "探索未至之境 / 预览版 / 选择工作区"。
- 在它上面点 `dsh-web`（工作区行）**无效**，仍停在选择页。
- 把第 1 个标签关掉再开第 6 个，仍然落在同一个空选择页（第 3 轮，5 个之后开第 6 个同样如此）。
- 三张表都指向同一个解释：**第 5 个客户端的会话数据通道没有建立成功**（不是渲染失败、不是内存不足——它只占 58–165MB，UI 框架完整渲染出来了）。

**机制未定位**（下一步的单点实验见第 6 节）。可能的两个方向：宿主对同一账号/同一分区并发 mux 连接有上限；或者应用层的"会话面板"只允许 N 个活跃客户端。对方案来说两者结论相同。

## 5. 对方案的影响

先纠正一个判断：第 4 节那个"只能开 4 个"**不是产品限制，是边界情况**。它只在"用户误开第二个同 host 标签"时才会被撞到，而正确做法是壳从一开始就不允许这种情况——所以它对方案的影响是"补一条去重规则"，不是"改架构"。

| 原方案假设 | 实测 | 改成 |
| --- | --- | --- |
| （原先假设同 host 可多开） | 不需要多开；且第 5 个会坏 | **同 host 单标签**，再点同一台机器 = 切到已有标签。这是产品规则，不是规避服务端限制 |
| "多标签内存可能翻倍，需要实测" | 每标签 ~170MB，隐藏后会被回收 | 上限按 host 计数而不是按窗口；休眠策略保留（销毁后台标签的 view，保留标签壳） |
| "服务端可能被多标签打爆" | 每标签 +4~5 连接，TTFB 不变 | 不是瓶颈，但连接数要计入宿主容量 |
| "标签上限导致需要丢弃策略" | 4 个就撞墙 | 上限设为 **同 host 1、跨 host 4**（跨 host 的上限由内存决定，~170MB/个） |

建议的页签规则（写进 T0 验收）：

1. **同一台机器只保留一个标签**：再点同一台机器 = 切到那个标签（浏览器里"已打开的页面"就是这样）。
2. **不同机器/服务可以并行**，但同窗口活跃标签软上限 6（内存约 1GB），超过后提示并建议关闭。
3. **标签丢弃**仍然要做：后台超过 10 分钟销毁 view、保留标签与 URL；但**不要**用丢弃来规避"同 host 只能一个"——那条是服务端行为。

## 6. 还差一个实验（30 分钟）

要定位第 5 个标签失效的机制，只需一个对照：

- **变量**：每个标签用**独立分区**（`persist:tab1`、`persist:tab2`…，即每个标签一套 cookie）。
  - 如果第 5 个变正常 → 上限跟"同一身份/同一分区"绑定（服务端按会话限流），壳里可以用"同一身份"来判定，规则就是"同账号同 host 单活跃"。
  - 如果仍然失效 → 是宿主对并发的硬上限，需要去 DSH 宿主侧查（这会影响整个产品的多窗口能力，不只是页签）。

这个实验的结论决定"同 host 单活跃"是产品规则还是权宜之计，建议开工 T0 前做掉。

## 7. 复现方式

测试脚本未入库（临时目录），方法可完整复现：Electron 起一个隐藏窗口，循环 `new WebContentsView({ webPreferences: { partition: 'persist:bench' } })` + `loadURL('http://127.0.0.1:3080/')`，每个等 9 秒后读 `app.getAppMetrics()` 与 `document.body.innerText`，同时用 `lsof -nP -iTCP:3080 -sTCP:ESTABLISHED | wc -l` 采样连接数。
