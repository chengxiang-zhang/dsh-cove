# 托管协调：代替老板推进 Agent 工作

职责：持续承担事项与长期职责的结果责任，统筹多个项目、机器和 Agent，把观察转成有依据的下一步。目标设计，尚未声明实现。

边界：秘书不承担业务实现或深度代码调查，可通过受控只读引用核查精确版本的 diff、测试和运行证据；不拥有任意 shell 或业务代码写权限。专业工作交给 [专业团队](14-专业团队协作.md)，秘书组织、监督并对总结果负责，不绕过执行端操作机器，不自行扩权，不直接发送对人消息。模型进行理解与计划，宿主校验操作并持久化。

协调依据 [领域模型](02-协议.md#领域模型与扩展) 组织跨项目工作：需求描述结果，事项/Task 承担完成责任，专业分工将职责交给 Worker。项目与会话不构成强制层级，扩展领域不能产生绕过当前责任账本的第二队列。专业策略、观察源和工作方法按 [插件契约](16-架构与扩展.md#插件契约) 注入。

## 承接与持续责任

接到事项时建立目标、可验证结果、交付位置、项目范围与授权引用。可从上下文和仓库规则确定的内容自行补齐并留出处；实质产品分歧给出推荐方案，不能让老板选择执行器、重试次数或技术故障处理方法。

长期职责还需要期望状态、观察来源、允许自主发起的工作、复查时机与暂停条件。接管时由系统盘点已有项目、会话和约束形成可审阅的职责描述，不把初始化变成老板填写配置表。

一个 Superagent 统一负责；项目、职责、事项分别有状态，不强制每项目常驻一个 Agent。委派临时协调者时必须限定事项、可用资源、回报方式及停止条件；不能转授超出原授权的能力。

## 秘书如何组织专业工作

秘书维护目标到专业责任、交付物、验收和交付步骤的可追溯关系，具体角色职责归 [专业责任与交付验收](14-专业团队协作.md#专业责任与交付验收)。每次受理、目标追加、风险变化或角色交接时重新检查责任覆盖，不把「已有实施者」当作团队齐备。

| 秘书动作 | 组织要求 | 如何证明有效 |
| --- | --- | --- |
| 建立目标 | 保留用户原问题，组织产品、技术、质量及适用体验/运行角色补齐场景、约束和风险 | 合同覆盖原问题，未知项有调查而非被默认省略；工程指标能解释实际目标 |
| 配置团队 | 检查专业能力、工具、上下文与独立性，给每项责任指定负责人；明确兼任和不适用理由 | 团队分工有来源、产物消费者与检查点；关键判断不由一个上下文包办 |
| 编排工作 | 按依赖和风险安排调查、原型、设计、实现及持续验证，尽早验证整合切片 | 不让质量只在末端出现，不让所有角色串行审批；跨项目接口有责任人 |
| 管理专业决定 | 技术问题交对应负责人，分歧组织独立复核和实验；影响合同按协议修订 | 决定有证据、适用版本和受影响分工；不把投票或秘书偏好当技术结论 |
| 监督与纠偏 | 对照预期证据检查进展、偏航、空跑和质量遗漏，明确诊断、操作与复查 | 纠偏被原线程消费，后续行为与成果改变；没有改变则修订诊断 |
| 收口交付 | 回收精确成果组合和独立结论，补齐运行准备，兑现阶段汇报及观察责任 | 未关闭缺陷不可伪装完成；发布按具体候选向老板申请，获批后自主执行 |

复杂事项可委派交付推进角色管理局部依赖、检查点和整合，秘书持续掌握总体目标、跨项目资源和未解决风险。所有子分工进入同一责任账本，委派者有范围、检查点及回收义务；不能无界递归派「经理」或由两个协调者同时控制同一写域。委派交付推进者异常时，秘书先核实控制权和现场，再接续或交接。

向执行体提供的不是孤立一句提示词：同时交付原始目标、专业责任、输入与消费方、允许决策范围、产物与验收、工具/资源边界、已失败方法和预期检查点。专业材料互相矛盾时秘书组织责任角色对账；不要求老板拼接结论或充当技术仲裁者。

## 从方向到执行

1. 明确的方向型委托进入事项，保留原始目标，安排授权内调查与方案分工。讨论和随口想法按 [判断](08-判断.md) 归位。
2. 汇总跨项目证据和候选方案。将实质产品取舍集中成版本化裁定请求，说明推荐及默认动作。等待期间推进授权内且不依赖该裁定的工作。
3. 调查确认没有实质待决项且授权足够时，记录自主判断依据，确定合同并直接进入实施。确有待决项时，仅相关分工等待匹配当前方案的用户裁定；采纳后把决定写入合同，拒绝后重新组织方案。两条路径统一按 [协议](02-协议.md#长期职责与事项) 转移，不能把调查结束当成必经审批点。
4. 按确定的需求、验收和交付合同拆出带项目、依赖和检查点的工单，采用 [父子版本与整体验收契约](02-协议.md#目标拆解与整体验收)。涉及新项目时按 [世界模型](04-世界模型.md) 逐阶段接入或初始化。
5. 系统在已确定目标、范围、承诺和授权内调整分工、方法与顺序。新证据显示方向可能需要改变时，先调查和准备方案，涉及实质变更再请用户决定。
6. 发现评审退回或验证失败，按 [协议](02-协议.md#分工与执行尝试) 回投原生会话并跟踪消费，修复后按新产物版本复核。最终按原目标汇报证据；改善类目标安排效果复查，技术交付和实际改善分别记录。

## 完整操作循环

| 环节 | 核心判断 | 必须留下的事实 |
| --- | --- | --- |
| 定位 | 人指哪件事、哪个项目、哪个宿主或已有会话 | 目标引用、消歧依据、观察时间 |
| 理解 | 目标、约束、完成条件和隐含依赖是什么 | 需求版本、假设及来源 |
| 组织提示词 | 执行体已有何上下文、缺什么、要交付什么 | 交办版本、材料引用、验收合同 |
| 安排 | 复用谁、何时并行、哪处需要隔离 | 分工、资源占用、依赖与理由 |
| 观察 | 与预期检查点相比是否有真实进展 | 产物变化、测试变化、阻塞与新证据 |
| 接答 | 执行体的问题可自行回答、调查还是确需用户决定 | 原请求、判断依据、响应和解除证据；语义按 [协议](02-协议.md#执行端反向请求) |
| 纠偏 | 误解、缺信息、环境故障、方法无效还是正常等待 | 诊断假设、备选方法、操作及预期读数 |
| 回收 | 结果在哪里、与哪次执行和需求有关 | 产物版本、执行记录、未消费输入 |
| 验收交付 | 满足要求了吗、进入约定交付位置了吗 | 验收结论、交付回执或继续工作的原因 |
| 继续 | 是否推进后续依赖，职责效果是否改善 | 下一步或带触发条件的等待，经验引用 |

工具执行与事实快照可能过期；每个会改变外部状态的提案都带 expected_revision/epoch。失败重新观察再判断，不对同一过期快照重复操作。

## 主动工作从哪里来

观察源可包含 CI/测试、运行异常、Issue/反馈、已有 Agent 会话、依赖和安全维护信息，以及授权内定期检查。观察源注册时声明读取权限、范围、时效、去重键和最晚复查，避免「只要没有新事件就永远不看」。

发现先进入 finding：可复现证据、影响、所属职责、已有事项关联。根据影响与可处理性选择并入、正式受理、继续观察或有理由地不做。无证据的改进想法可先只读调查，不直接生成无限维护队列。

在职责授权内、目标明确的缺陷修复由系统自行受理执行。新产品方向、扩大职责或外部承诺不能借「主动维护」越权。没有值得处理的问题时保持观察；主动性不以任务数或工具调用数评分。

主动检查也按专业责任覆盖：质量关注回归与测试盲点，运行关注异常与效果，安全关注授权范围内的真实风险，架构关注已出现的兼容/容量问题，产品与体验关注已有目标中的实际使用缺陷。秘书判断价值、去重并排序，不要求各角色为了证明活跃不断生成建议；无依据的重构或扩功能不能冒充维护。

## 跨项目安排

统一看老板显式优先级、实际风险、期限、依赖、受影响范围、等待时长及资源可用性；具体排序是可解释的策略，不写死成项目轮询。老板未排序时系统根据已有目标排序，不把日常调度交回老板。

- 独立项目、独立写域可以并行；共享 checkout、分支整合或外部环境变更必须获得资源锁。
- 工作区形态服从各项目自己的规则；不得假定所有仓库都允许 worktree。
- 高优插单前先保全进展和资源；不能让被挤出的事项失去 next_review_at。
- 跨项目依赖显式保存满足条件和成果版本；检测环后重新安排或缩小单次分工，不擅自缩小总目标。
- 父目标变更后先核对拆解绑定，判定影响并重排；整体验收安排跨项目成果组合验证，不能把子单分别通过当作父目标通过。
- 每件延期事项记录原因、替代动作、最晚复查。持续延期触发重新排序，不能无声饥饿。
- 项目授权分别求值；同属老板或同属 NetBird 不代表可以跨目标执行。

资源争用的实施形态是宿主可执行的锁与租约，不是提示词里要求「别冲突」。

## 诊断与自主恢复

低工具调用、重复命令、耗时超过预计只是信号。先检查事件新鲜度、执行器是否仍活跃、产物与测试是否变化、是否等待外部动作，再形成诊断。

| 诊断 | 处置 |
| --- | --- |
| 正常调试或明确等待 | 保持执行，更新下一检查点；不因重复编辑杀掉会话 |
| 执行体等待回答或审批 | 接管待答责任，补读/调查后经 respond_request 回答；确需用户时准备具体问题并跟进，不能把原始技术问题直接转交老板 |
| 理解偏差或交办缺上下文 | 修订交办，给出具体纠偏，确认新输入被消费 |
| 可修复环境问题 | 安排环境修复或切换已授权环境，随后继续原事项 |
| 方法无效 | 切换方法或请求独立调查，带上已失败的方法与证据 |
| 执行器故障或上下文失真 | 保全成果、交接，再更换执行体 |
| 资源或外部依赖不可用 | waiting，保存恢复触发与最晚复查，继续推进其他工作 |
| 当前约束确实无法满足 | 用证据说明障碍及已考虑路径，保留成果；确实无法继续时 broken，不能假完成 |

同一失败签名无新证据或不同策略时禁止盲目重试；尝试预算到线先停止或保全该尝试，再诊断责任如何继续。等待要周期性重新评估可行性，不用定时空回合冒充推进。策略重试预算由可解释策略控制并可在有新证据时调整，不采用「固定三次等于目标失败」。

系统不能以恢复为名自行降低验收、取消需求或创建同义事项重置失败计数。无法自主消除的授权缺口与真实产品取舍才找老板；其余失败可以如实交付无法完成结论，但不要求老板接手诊断。

## 监督信号与纠偏闭环

秘书既监督执行者，也监督交付推进、专业负责人和验收者。每个检查点写清要消除的不确定性或要出现的成果证据；工具次数、代码行数、工单完成数和持续说「正在处理」均不能替代目标进展。程序负责唤醒、心跳、版本及重复信号检测，语义判断负责解释，不以单一阈值处罚正常调试。

秘书自身也必须受检查：宿主持久复查到期未处置、重复决策却无新证据、未兑现纠偏检查点及长期缺负责人的事项，按预先登记的监督策略触发独立协调诊断，不依赖秘书主动承认空跑。这些信号只触发核查，不能自动判失败；已确认的暂停、人工接管与有效等待不算失职，监督换代不得恢复用户已停止的工作。诊断角色读取目标和原始轨迹，给出偏差及修正提案；它无权另建控制面、改写质量结论或绕过权限执行。确需替换失效协调席位时沿内核租约和恢复契约隔离旧写者，从同一账本恢复，保留老板面对的同一秘书及责任；诊断自身也有预算与检查点，不递归创建无限监督者。

| 信号 | 秘书组织的处置 | 纠偏解除依据 |
| --- | --- | --- |
| 报告忙碌但无新成果/假设 | 核查真实回合、待答请求、产物与实验；需要时派独立诊断 | 新证据排除假设、成果向目标推进，或形成真实等待；重复报告不算 |
| 代码正确但偏离用户目标 | 请产品与质量对照原问题定位缺口，必要时由架构/体验修订方案，回投实现 | 原始场景在新候选上成立；不能只新增无关指标 |
| 秘书开始代写或只转发消息 | 工具围栏拒绝越界；核查专业分工是否缺失、交办是否清楚并补齐 | 业务改动来源是获授权专业执行者；秘书仍有实质组织、诊断与回收记录 |
| 声称完成但证据不足、篡改判据 | 阻止依赖该结论的交付，安排独立原始证据核对；检查受影响历史结论 | 当前版本独立重验，伪造或失效证据明确作废并追溯影响 |
| 评审苛刻、误报或与实现争执 | 要求绑定要求/风险、复现和解除条件；按专业团队的争议机制独立裁决 | 复验或反证支持结论；不能为了进度换一个愿意通过的评审 |
| 同类问题复发 | 对照历史失败与改进记录，检查未召回、未应用、方法无效或范围误用 | 专业改进有验证且后续任务实际应用，不能以新增一条记忆关闭问题 |
| 技术障碍长期未解 | 明确仍未知的假设，组织领域调查/实验、能力修复或更换已验证执行端 | 新方法带来证据，或对当前约束下不可完成形成独立核验；不让老板选择重试方案 |

每次纠偏保存触发事实、诊断假设、负责角色、具体改变、预期证据、原生输入消费、复查条件和结果。复查无改善时必须更新假设或方法，不循环发送「继续」「认真」「按生产级做」。需要替换角色先保全并交接；正常返工保持原执行及原评审线程。

`broken` 不能成为摆脱困难的出口：须由对应专业给出障碍与反例，秘书核对已探索的合理路径、尚可推进部分和能力修复可能，重要技术结论再经独立核验。仅有重试耗尽、模型信心不足或评审争执不满足条件。确证当前约束下无法完成时如实终止该事项、保留成果与后续触发；长期职责仍持续，除非用户撤销。报告失败不要求老板接手技术排障。

只有实质目标/承诺选择、超出既有授权、本人专属体验、具体发布授权或原生机制要求本人完成的操作才形成用户待办；其他问题由内部角色解决。告知风险与要求决策分开，用户没有回复不阻断无依赖的授权内工作。经验改进的责任和生效路径归 [规则](06-规则.md#专业复盘与防复发)。

## 人工介入与职责暂停

用户的明确停止优先于调度。暂停与进度状态正交，默认范围按协议：暂停职责阻止新事项并暂停专属在途工作，不误停独立委托的共享事项；明确停止事项转 released，原始成果与输入保留。含糊的「停」先用当前明确焦点定位，无法唯一定位时只问范围，不猜测全局停机。

用户停止的事项及关联 finding 保存抑制记录：同一目标、同一问题与同一事实版本不能被主动扫描立即重开。新证据可以记录和评估，但要重新执行已取消工作，须有明确新委托或职责范围调整；不得借新 id 绕过停止。普通归还控制只解除 human_controlled，不解除 released 或 finding 的取消抑制；归还同时明确重新委托时才建立关联新事项。新出现的独立高风险事实可告知用户，不等于自动恢复已取消操作。

确认人在 GUI/CLI 接管会话时，系统停止自动写入并标为 human_controlled；继续只在明确归还控制后。外部取消来源未明时使用 [权属待核实的暂停](02-协议.md#长期职责与事项)，秘书负责调查并按证据决定恢复或继续围栏，不能让老板归还从未接走的控制权。单纯查看页面不算接管，缺少人工操作记录也不证明没有接管。不能用诊断循环把人停止的 Agent 再拉起来。

## 契约与依赖

```text
accept(intent, context) → commitment + contracts
reviewResponsibility(id, facts) → findings + decisions
schedule(snapshot) → versioned assignments + resource claims
advance(commitment, observations) → next action / wait / evaluation request
recover(commitment, diagnosis) → revised strategy with expected evidence
```

依赖判断、执行体、验收、规则、记忆、世界模型与内核。判断生成解释与交办，执行体完成协调操作，验收给结论，内核保真；本模块统一决定下一步。没有任何下层模块直接调用本模块形成环。

## 失败模式与验证

最危险的失败是「账本没丢，但事情没人推进」。检查非终态事项与职责是否有可执行下一步、有效等待或确证的无法完成；仅 next_review_at 非空不够。

验收应证明无人催办闭环、跨项目插单不遗忘、错误提示词能被修正、同一失败不盲重试、坏产物被退回以及人工接管不被夺回。可扩展观察源和协调策略，但不能绕过授权、资源锁、验收或停止语义。


## 本地开发维护入口

`web-all.config.managedWork.bootstrapFile` 指向宿主所有者管理、禁止其他用户写入的 JSON 文件。宿主在文件中配置 `root`、`defaultProject` 与 `projects`：每个项目登记真实仓库路径、可读源码、允许修改路径、原生 Codex 配置、独立验收方法及其当前资格、项目门禁依赖和工具。凭据只由宿主复制到任务私有原生环境；提交者不能通过请求指定执行程序、凭据、源码封存或资格结论。

启用后，受信浏览器客户端通过 `GET /superagent/managed/projects` 查询项目，向 `POST /superagent/managed/intake` 提交 `{ "requestId": "客户端唯一请求标识", "project": "已登记项目 ID", "text": "需求" }`，再向 `POST /superagent/managed/status` 提交同一 `requestId` 查询状态。三个接口都使用共享 Host、会话与同源围栏。相同请求标识及内容只接收一次；相同标识配不同内容拒绝。飞书单聊复用同一持久接收入口：普通文本使用默认项目，`/work 项目ID 需求` 指定项目；一条消息由托管或旧协调入口之一处理。接收成功表示已入队，不表示业务完成。

宿主异步启动真实协调、实施和独立质量线程，按项目已配置的方法验收，再对候选完整 Git tree 执行固定项目门禁。全部证据仍有效时才经受控端口向本地 `dev` 提交，并仅对交付路径对齐工作树及主 index；其他用户改动保留，同路径并发变化拒绝覆盖。完成报告重核当前验收、门禁隔离持有者、Git 提交及落地文件，不代表推送或上线。每个任务结束后停止自己的原生进程并清理复制的凭据。

当前内置首个业务验收方法为 `codex-runTurn-replay@1`，适用于 Codex 回合解析维护；项目与事项入口、派工、项目门禁和本地交付复用同一主链。未配置匹配且有效的方法时报告能力缺口，不把其他业务当作解析器回放验收。需要恢复的未知操作保留原记录，宿主重启后在途 admission 标为待对账；不会自动重放可能已发生的副作用。一次业务完成不关闭独立的上级平台开发要求。


同一事项在 `needs-attention` 状态可通过受信 `POST /superagent/managed/continue` 提交 `{ "requestId": "原请求标识", "continuationId": "本次补充的唯一标识", "text": "补充指令" }`。宿主将指令与当前只读材料版本持久化后串行续接原账本和原生线程；相同补充标识只执行一次，内容或材料版本冲突拒绝，在途事项拒绝并发续接。材料路径、来源和 SHA256 只从宿主配置的 `readOnlyMaterials` 读取，请求不能声明可信身份或提交任意读取路径；材料进入可追溯上下文，不进入候选或 Git 交付资产。

框架基线发生变化时，宿主配置精确 `frameworkBaselineTransition`，核对旧写者停止、前后公开业务源码 blob/mode 一致并记录变更依据。普通续接要求操作完成且候选未修改。对经授权的验收分工修正，`contractPartition` 绑定精确合同与角色版本、候选 SHA256/模式及旧操作：原质量线程须结构化批准业务判据与交付判据映射；每个未完成执行槽须有停止回执和原输入对应的中断终态。宿主事务保留原要求、判据正文、未决问题和旧操作，更新责任范围，只允许原线程在新范围承接候选。缺证明或并发变化均拒绝，不把中断记作业务成功。

业务 `criteria` 由独立方法完整验收；`deliveryCriteria` 由同树全部项目门禁与真实本地提交回执承担。编译上下文同时展示两类要求，交付前和结果报告时复核工程证据；移交后的团队须重新取得独立质量批准。
