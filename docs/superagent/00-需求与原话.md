## 附录 A 老板原话（逐字，本文的最高权威）

**权威顺序：本附录 > 正文 > 任何转述。** 正文与本附录冲突时，以本附录为准，并把冲突交回老板。
标〔原文如此〕处保留原始写法（含笔误），下游不得修正后再当原话引用。

1. 「我们两个都有的一个问题是，在我看来router做的都不好，我们继续讨论（私聊每个人*bot或者不同群聊）应该对应不同的对话，对话本身就是router（会话+专属记忆），router只管理分发汇报的工作，禁止处理具体事务，分发应该是判断是临时还是长期事务，临时就走subagent，长期应该用agent team」
2. 「super agent就和一个人类一样在工作，有协同接受别人的任务，会拒绝，会派活，同时也会主动汇报可能的问题，会按照目标自驱输出方案，人类批准后自己安排其他agent去干活」
3. 「你可以认为router就是个一个项目经理或者秘书的岗位」〔原文如此，重复“个”〕
4. 「秘书既承接老板的话，也作为老板多的代表承接其他人的活」〔原文如此，“老板多”应为“老板的”〕
5. 「不是每对话一个 Router，不同人的私聊需要有各自的对话，不同的群聊需要有各自的对话，同一个人在私聊和群聊里面的记忆是共享的，其实主要的目的是记忆不混乱不冲突，同时隐私不泄露」
6. 「暂时是我一个人，但是我可能会拉到群里帮我解决问题，承接更多人」
7. 「判据：接受升级制（按 Thread 归属）」
8. 「代价接受，希望 router 能针对接到的问题做判断，使用什么 agent 和模型」
9. 「感觉router和会话处理还是很机械，我们什么时候做4 架构 B」
10. 「为什么你都不测试下super」
11. 「你可以基于调研结果补全升华我的需求，我前面给你的都是打比方和举例子；你应该挖掘我背后需要的到底是什么」
12. 「总结下我的需求，帮我补全，你再后半段的回复质量太低了」
13. 「你让opus55来设计具体的产品技术方案，并归档清理合并我们讨论过程中的所有文档，保留唯一的设计文档就行了」
14. 「追求全自动，super agent 应该在和我的交互中逐渐磨合出来」
15. 「做面板 UI，这个是需要的，但是不高优，因为有时候我不太相信自迭代的能力，我害怕agent空跑，转牛角尖，如果super agent 能做好协调其实可以没有」
16. 「Router 不读代码，但是应该读交接文档，所以是否应该有文档交接区，Router做的是上传下达的工作，是协调的工作，信息来源应该是人的输入，agent的协调和汇报消息，已经交付文档等」
17. 「你给opus55足够的上下文，让他重新设计吧，我感觉你现在的设计平平无奇」
18. 「我需要每次和它说话都像和同一个人说话」
19. 「投机执行（后台先做、没用就静默丢弃）和全双工是需要的，我们当前根本不需要考虑token成本恩替」〔原文如此，“恩替”应为“问题”〕
20. 「router的注册机制怎么处理呢？？比如知道可以做哪些范围，比如本机、以及netbird网络里面的所有机器的范围，知道存量都有什么，知道用户口中说的具体指哪个东西，知道哪个需求是需要新建工作区的」
21. 「是router的规则注册问题，以及规则自迭代的问题」

**由原话直接推出、不属推断的硬约束**（正文冲突即为缺陷）：
Router 是岗位不是组件（3）；产出是判断与分配不是执行（1）；要有人的工作方式，含拒绝与主动报忧（2）；
同时替老板和替他人办事，两个方向责任不同（4）；全自动靠交互磨合长出来，不是出厂配置（14）；
老板对空跑与钻牛角尖的恐惧是设计输入，可观测与一步干预是必选项（15）；
信息面 = 人的输入 + agent 的汇报与协调 + 已交付文档，不含代码（16）；记忆跨对话共享、按可见域隔离（5）。
