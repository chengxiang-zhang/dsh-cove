# Superagent：跨机器、跨项目的 Agent 工作托管

Superagent 是统一面向老板、跨项目承担结果责任的秘书。它从明确委托或长期职责出发，按目标和风险组织产品、架构、体验、交付、实现、质量、专项及运行专业责任，协调多个项目和 Agent，负责监督、纠偏、验收推进与汇报。飞书和网页是同一秘书的入口。首期服务一位老板，从当前项目开发维护开始，并用第二个项目验证跨项目交付。

## 设计状态与权威

本目录是依据 2026-11-09 需求澄清修订的**目标设计**，不代表这些能力已经实现或部署。现有实现包含通道、承诺账本、执行端 transport 与恢复等基础；是否满足目标必须按 [验收与评估](13-验收与评估.md) 取证，不能用旧测试通过代替。

权威顺序：[需求原话](00-需求原话.md) > [需求基线](01-需求基线.md) > [协议](02-协议.md) > 模块文档。`plan/` 保存原实施批次材料，其顶部适用性声明优先于其中的冻结、波次与 DONE 结论；它不再是本目标设计的施工清单。

双形态托管、秘书工作边界和 Codex 原生续聊要求归 [需求基线](01-需求基线.md)。模块划分、逻辑对象、调度与评估机制属于目标设计。

## 两种托管，一套责任体系

| 形态 | 输入 | 持续责任 | 结束条件 |
| --- | --- | --- | --- |
| 事项 | 老板交代的结果，或职责内发现的问题 | 明确验收、安排执行、纠偏、回收、验证、交付 | 验收及约定交付完成，或有依据地终止 |
| 长期职责 | 负责范围、目标、观察源、行动授权 | 持续观察、判断价值、发起事项、验证效果、再次观察 | 老板暂停、撤销或调整职责；会话结束不结束职责 |

长期职责可以覆盖多个项目；项目可有多个机器副本和多个 Agent 会话；事项可以横跨项目。项目、目录、会话和聊天线程都不能充当责任的唯一主键。

不需要老板反复派活、催办、重讲上下文、选择技术重试方案。老板仍能主动讨论、改变方向、查询或接管。全自动适用既有授权；不自动扩权、不降低验收标准、不隐瞒无法完成。

## 架构选择

| 路线 | 优点 | 主要代价 | 本方案取舍 |
| --- | --- | --- | --- |
| 固定工作流与规则驱动每个判断 | 容易审计固定动作 | 工作理解、提示词和纠偏不断长出特例；难承载未知情况 | 只用于硬边界和确定性事务 |
| 单一长驻会话直接持有全部状态与工具 | 原型快、操作灵活 | 状态、权属与恢复依赖上下文；跨项目污染与失控难定位 | 不采用 |
| 模型承担理解与协调，程序保障状态、权限、操作与恢复 | 接近老板真实操作循环；执行体可替换而责任不丢 | 需要高质量证据、明确协调工具和端到端评估 | 采用，保留既有可靠性底座 |

不是给每个项目常驻一个项目经理。复杂工作可以委派交付推进角色，但它同样是有范围、有交接、有回收责任的执行体，不能产生另一个无主工作队列。专业责任持续覆盖，执行席位按需合并或拆分；质量工程从设计期介入，关键结论独立验证，职责、交付物、验收和方案取舍归 [专业团队协作](14-专业团队协作.md)。

## 主循环与模块

```text
人类消息 / 项目与运行观察 / 到期复查 / Agent 结果与待答请求
                    ↓
        归一与认领 → 持久化事实及待处理信号
                    ↓
  桌子编译上下文 → 判断理解 → 托管协调决定下一步
                    ↓
       协调操作意图 → 宿主校验授权、版本与资源
                    ↓
   定位 / 派发 / 续接 / 接答 / 纠偏 / 诊断 / 回收 / 验证
                    ↓
       远端事实与证据 → 验收 → 交付或继续推进
                    ↓
      职责效果复查、经验更新；对外消息统一出口
```

每条链路都保存来源、责任、预期结果和操作回执。模型决定做什么以及为什么；宿主决定这次操作是否合法、是否已执行、是否仍针对正确版本。

授权内无实质待决的调查结果直接进入实施；执行中的反向请求由秘书接答，跨项目拆单按父目标版本与成果组合验收，主观体验在正式交付前准备候选。相应状态与边界统一归 [协议](02-协议.md)，真实连续托管的验证归 [验收与评估](13-验收与评估.md)。

## 依赖与代码归属

全部宿主行为仍属于 `packages/dsh-web-all/src/host/services/superagent/`，不增加运行时实体，不修改 DSH 源码。保留 `channels/feishu`、`executors/transport/{http,inproc}`、账本与恢复的归属。专业角色通过版本化分工和执行 profile 组织，不按人类岗位复制宿主模块。`coordination/`、`context/` 与 `verification/` 提供领域协调、上下文编译与独立验证模块；完整托管入口和生命周期仍须按 [实施路线](15-实施路线.md) 接线和验证，目录存在不代表无人交付已经完成。

逻辑依赖方向（箭头表示通过契约调用；实现由组合根注入，不直接 import 对方插件私有实现）：

```text
组合根：装配各端口与事件，不含业务判断
桌子 → 判断、托管协调、规则、记忆、世界模型、内核
托管协调 → 判断、执行体、验收、规则、记忆、世界模型、内核
判断 → 规则、记忆、世界模型、协议
执行体 → 世界模型、内核、协议
验收 → 世界模型、内核、协议
时机与措辞 → 规则、记忆、内核、协议
恢复 → 世界模型、内核、协议（通过注入端口读取与核对会话）
规则、记忆 → 世界模型、协议
世界模型、内核 → 协议
```

验收提出验证任务，托管协调安排执行，验收不直接调用执行体。判断只产出提案，不直接派发；恢复提交需重新诊断的事实，不自行替用户重新开工。下层不会回调模型协调逻辑；事件经组合根归一。

## 扩展与实施边界

业务能力与外部依赖通过版本化插件契约装配，内置能力使用同一入口。愿望、需求、项目、事项/Task 和 Worker 的语义归 [领域协议](02-协议.md#领域模型与扩展)；插件边界、宿主与引擎替换、上下文投影、热更和迁移归 [架构与扩展](16-架构与扩展.md)。首期保留单一运行时实体，逻辑插件不代表独立 Cordis 实体。

设计迁移要覆盖：职责与多项目关联、协调操作及控制租约、验收对象、线程归位、语义学习与消息策略。现存全局单槽位、固定九工具、统一 100 词、三次失败终止、同窗口指纹一致等约束不能继续作为新设计的验收目标。

技术实现必须先验证目标宿主实际能力。缺能力如实展示并安排授权内的适配工作，不能静默回退到不满足要求的执行模式。上线或重启是否必要按 [HMR 契约](../hmr.md) 判断；文档修订本身不改变服务。
