# 72 小时不变量、失败落点、最可能错的地方

> **本文属于《秘书式 super-agent 设计文档体系》**，覆盖全局 §10、§14。索引与权威顺序见 `README.md`。
> 线上出问题时读这一份；它也列出了这个设计自己最可能错在哪。

## 10 72 小时无人值守：不变量与失败落点

### 10.1 不变量（任何时刻成立，验收 SQL 在 §13）

- **I1 不遗忘**：每件 `proposed/open/at_risk` 承诺都有 `next_look_at`（CHECK），且非 goal 类 `next_look_at ≤ now + 24h`，goal 类 ≤ 7 天。
- **I2 一问一处置一答**：每条被认领的入站恰好一个 disposition；每条入站至多一条 reply 档出站。
- **I3 没有无主算力**：每个 `running` attempt 都属于一件未结案承诺，且有墙钟预算。反过来，任何执行体会话不在 `sa_attempts` 里就不是秘书的。
- **I4 一个声音**：所有出站都带当前租约 epoch；同库多进程只有持有者能发。
- **I5 账本即真相**：重启后"谁在跑什么"只由账本加 `inspect` 重建，不依赖进程内存。现有 `bot-sessions.ts` 的进程内 Set〔已证实：第 19 行〕对秘书会话不适用：秘书会话角色按 `cwd`/`session_id` 查 `sa_desks`/`sa_attempts`，经解析器注册给 `isBotSession`，避免执行体跑完被 responder 当成外来会话触发主动通知〔已证实：`responder.ts:1357-1361` 的 `observeForeignTurn` 分支〕。

保证手段：60 秒议程扫描（宿主信号预检）；启动对账（顺序：建表 → 抢租约 → 注册角色解析器 → 对账 → 接新触发）；租约心跳 15 秒、过期 60 秒；桌子会话按事件数 4,000 或跨日换代，换代零成本因为真相在账本；跨天时受理里的时间写绝对值（"明早 9 点前"）。

### 10.2 失败落点

| 失败 | 谁发现 | 对外说什么 | 怎么恢复 |
|---|---|---|---|
| 执行体停滞（10 分钟零工具调用，两窗口） | 议程扫描 | 无（silent）；升级后按升级结果 | cancel，`cancel_origin='stall'`，进升级 |
| 执行体打转（同 command / 同文件 edit ≥3 次） | 事件订阅累加 `repeat_count` | interrupt 一次："C-n 在反复改 X（第 4 次），1 继续 / 2 停" | `at_risk`，`ball=owner` |
| 预算 80% / 100% | 事件订阅 | 80%：brief（老板在等则 interrupt）；100%：interrupt"到线了，做到 X，1 再给 N 分钟 / 2 停" | 100% 自动 cancel，`at_risk` |
| 执行体失败 | 结案判定 | 两次自动恢复都失败才说话 | 升级三选一，按序：同执行体重派（`interrupted/error/stall` 且 n<2）→ 高一档执行体（`max-tokens`、自报 failed、或已重派）→ 问老板一个问题（n=3 或无更高档） |
| 秘书回合失败或回合结束仍有未处置消息 | 桌子 `turn/end` | 第一次：重试，不说话；第二次：宿主模板"这条我没处理好，请再说一次" | 处置记 `decided_by='host'`；计入 `tool_errors` |
| 秘书 30 秒内没受理 | 宿主计时器（20 秒） | 先打已读表情（不是消息） | 回合继续；超 60 秒仍无 `say` → 宿主模板受理"收到，正在判断" |
| 进程重启 | 启动对账 | 每件被中断的至多一条 interrupt："C-n 因重启中断，停在第 N 回合，改动在分支 X。1 重派 / 2 放弃" | `inspect` 失败 → `orphaned`；会话在且最后是 `turn/end` → 补判；会话在跑 → 保持 |
| 租约被别的进程持有 | 抢租约失败 | 无 | 本进程只判断不发送（等价 shadow），日志报警，`status` 显示持有者 |
| 出站发送失败 | 发送端 | 放弃后在下一条出站末尾附"有一条消息没发出去" | 沿用 responder 的 30 秒起、24 小时放弃退避，同一 `idem_key` 作 uuid〔已证实：`responder.ts:75-87`〕 |
| 飞书重投 | `inbox_events.message_id` 唯一 + `sa_intake.message_id` 唯一 | 无 | 插入冲突即丢弃〔已证实：`inbox-store.ts` 部分唯一索引，§5 读数 `idx_inbox_events_message`〕 |
| 盯的远端会话读不到 | `watch` 探针 | 连续 3 次读不到 → brief 一行"pc-tower 读不到了" | 承诺转 `broken`，不重试到无限 |
| 秘书自己空跑（议程回合 `ops=0` 占比高） | `sa_deliberations` 日统计 | brief 一行 | 宿主收紧信号阈值，见 §14 错误 7 |

### 10.3 跨机的第二个声音

同库租约挡不住另一台机器上用同一飞书应用的实例（Hermes 就在 Linux 上〔已证实：brief §02 B〕）。本设计的处置是**发现**而不是**防止**：每次 reply 档出站后 30 秒，宿主读一次该会话最近消息，统计本应用发出的、`reply_to` 同一入站消息的条数；大于本库 `sa_outbox` 记录的条数 → 判定有第二个实例，interrupt 老板一次并在 `status` 标红〔未验证：所需的读消息历史权限与接口在本应用上是否已开〕。防止只能靠运维：一个飞书应用只给一台机器的凭据。

## 14 这个设计最可能错在哪

**错误 1：案卷对寒暄主导的负载太重。** 现象：受理中位数 >20 秒；`sa_deliberations` 里 `trigger_kind='intake'` 且处置为 `answer/acknowledge` 的回合占 token 的大头。发现：`SELECT disposition, avg(dossier_tokens), avg(ended_at-started_at) FROM sa_deliberations JOIN sa_intake ...` 按处置分组，P0 第一周看。改哪里：扩快路径 3 的白名单；或给 `answer` 处置一个不带判例段的瘦案卷（只有在办与本批）；最后手段是桌子会话用最低档模型、执行体才用强模型。

**错误 2：声明式假设让老板更累，不是更省。** 现象：`overturn_rate` 在多个类上 >25%，或老板开始在第一条消息里就把细节写满（他在防它猜错）。发现：P1 的 `sa_classes.overturn_rate`；每件承诺老板参与次数不降反升。改哪里：§3.4 规则表——把"涉及哪个文件/哪个仓库"类假设改为强制问；或者全局默认 `ask_mode='ask-first'`，让校准把可信的类放回 `declare`（升要证据的方向反过来）。

**错误 3：工作类太碎，校准永远攒不够样本。** 现象：第 30 天各类样本中位数 <5，`eta_factor` 几乎全是 1.0，第 2 月的成长不出现。发现：`SELECT median(samples) FROM sa_classes`（用排序取中位）每周看。改哪里：关闭 `origin='desk'` 的新建（`CLASS_QUOTA=0`），只留 8 个种子类；或者校准退一级，按 `check_kind × executor` 四到八格计算，不按语义类。

**错误 4：案卷漏掉了相关的那条约束，老板还是得重讲。** 现象：老板消息里出现"我说过""上次说了""又"；或交付违反一条已存在的 constraint。发现：intake 文本扫描这几个词并与当时案卷的 `dossier_hash` 对照，看那条 memory 是否在案卷里。改哪里：老板的 constraint 条数很少（预计 <30〔推断〕），改为全部无条件进案卷、不做相关度筛选；相关度筛选只用于 precedent 与 person。

**错误 5：注意力分档分错。** 现象 A：老板说"怎么没告诉我"——该打断的进了简报。现象 B：简报连续多天无人回复、其中的编号决定过期——简报被无视，等于把事情埋了。发现：A 靠 intake 文本扫描"怎么没/为什么不早说"；B 看 `ball=owner` 的承诺在简报里出现 ≥3 次仍未处理的数量。改哪里：§9 规则表；B 的情况把"在简报里出现 3 次未处理"的事自动升为一次 interrupt，并把每日额度从 3 调到 4。

**错误 6：用与说分离在群里仍会泄露。** 现象：群里的回复里出现只有老板私聊里说过的信息的**改写**（字面比对抓不到）。发现：金丝雀只能抓字面；另每周从群出站里抽 10 条，与该期间老板私聊的 `say=[owner]` 记忆一起给一个只读评审执行体判断有无语义泄露，结果进简报〔推断：评审本身也会漏〕。改哪里：群桌子的案卷不给不可说记忆的原文，只给宿主从它派生的一句判断提示（例如"回复要短"而不是"老板说过他讨厌长回复"）；仍泄露则群里完全不进 person 记忆，回到 v1 的做法并接受违背原话 5 前半句，届时交回老板裁定。

**错误 7：议程时钟让秘书自己空跑。** 现象：`trigger_kind='agenda'` 的回合 `ops=0` 比例 >30%，或每日秘书 token 超过执行体 token。发现：P2 的 deliberations 统计（§13）。改哪里：§3.7 的信号预检更严（只在跨越校准 ETA、停滞、打转、汇报到达时起回合，单纯"时间过半"不起）；`next_look_at` 推后用指数退避。

**错误 8：老板其实不想要承诺语言。** 现象：他从不说"C-12"，受理里的编号与"按 X 理解"被他当成噪音，或他直接说"别每次都复述"。发现：老板消息里引用承诺编号的比例；直接的负面原话。改哪里：受理去掉编号只保留假设一句；编号只在他要停或问进展时出现。承诺账本不变——它是给宿主和老板验收用的，不是给他读的。

**错误 9：盯会话的探针读不到远端，或读到的信号不足以判断空跑。** 现象：`watch` 承诺大量 `broken`；或判了空跑但老板看了说"它在想，没空跑"。发现：`kind='watch'` 的结案状态分布；interrupt 后老板回复"没空跑/继续"的比例。改哪里：空跑判据从"零工具调用"改为"零工具调用且 assistant 文本与上一窗口高度相似"；远端读不到则把 `watch` 降为"老板问时去看一次"，不承诺持续盯。

**错误 10：`now` 编错，一次污染所有桌子。** 现象：老板在两个对话里得到互相矛盾的答案；或他刚说完的约束在另一张桌上不生效。发现：`now_hash` 断言通过但内容错——抽查 `now` 渲染结果与账本实际状态是否一致（每日 1 次，比对 `sa_commitments` 的球权与 `now` 里的球权）。改哪里：`now` 生成改纯函数 + 快照对比测试；出现不一致时**降级为单桌案卷**（回到 v2 行为），宁可"不是一个我"，也不给两个互相矛盾的答案。

**错误 11：投机变成后台烧钱机器，且从不出成果。** 现象：`sa_speculations` 里 `discarded/(used+discarded)` 连续一周 > 80%；或老板问"你刚才在算什么"频率上升。发现：每周按 `kind` 分组统计采纳率。改哪里：先关第 3 类（空闲巡查），只留第 1 类；`hypothesis` 字段加严格校验（它必须复述老板说过的意图，不能自造）。

**错误 12：全双工退化成"它一直忙，你一直等"。** 现象：承诺在跑时发寒暄，`p95` 比空闲时差 > 3 秒；`trigger_kind='msg'` 的排队占比 > 5%。发现：§16.3 的两条读数。改哪里：把议程回合的顺延上限从 5 次提到 20 次（人的消息永远优先）；必要时给对话桌单独留一个执行槽，不与承诺抢。
