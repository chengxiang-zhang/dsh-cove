# 恢复与降级：坏了还能做什么

职责：让系统在重启、热更、会话丢失、租约冲突、渠道故障里继续正确工作，并把"现在处于降级态"变成可读的事实。

边界：不判断、不发送、不重写账本。它只做三件事：对账、修复、降级。

## 五条不变量（任何时刻成立）

- I1 不遗忘：每件开着的承诺都有 `next_look_at`（协议表级约束）；非目标类 ≤24 小时，目标类 ≤7 天。
- I2 一问一处置一答：每条被认领的入站恰好一个处置；每条入站至多一条 reply 档出站。
- I3 无主算力：每个 running 尝试都属于未结案承诺且有预算；不在账本里的会话不是我们的。
- I4 一个声音：所有出站带当前租约 epoch；同库多进程只有持有者能发。
- I5 账本即真相：重启后"谁在跑什么"只由账本加 `inspect` 重建，不依赖进程内存。

## 启动顺序（固定，不能换）

```
建表/迁移 → 抢租约 → 注册角色解析器 → 对账 → 接新触发
```

顺序的意义：先有真相，再有身份，再修状态，最后才接新消息。反过来的话，重启后的第一条消息会撞上一个还没对账的账本。

角色解析器：把"这个会话是谁"从进程内 Set 升级成函数 `resolveRole(sessionId) → bot | desk:<id> | executor:<id> | undefined`，内部可继续用内存映射（角色本来就可从账本重建），保留现有 `isBotSession` 的读取点不动（F20）。今天的 Set 在启动时会按账本重建，真正丢的只是从未落过绑定的会话——所以这一步是补齐，不是推倒。

## 对账：tick 拉，不只启动时做

历史评审的教训：只在启动对账，热更窗口里丢掉的 `turn/end` 永远不会被补（FMEA-4）。所以对账挂在时钟上，每一轮都做：

1. 扫所有 running 尝试：最后事件时间超过 N 分钟（默认 10）或事件流异常 → `inspect`。
2. 会话不存在 → 标 `orphaned`，承诺转 `orphaned`，主动报一条（每件至多一条）。
3. 会话存在且最后一个回合已结束 → 补结案判定。
4. 会话存在且还在跑 → 保持，不打扰。
5. 桌面会话对应关系对不上 → 换代并从账本重建案卷。

## 热更与工具面自检

热更（用户重启后新代码生效）会带来两个已知退化：桌子工具面可能退回全工具（FMEA-11），以及闭包指向已关闭的连接。

两条机械检查：

- 每次桌子回合开始前自检：可见工具集必须恰好等于桌面工具集；不等于则 **fail-closed**：本回合不跑，记一条告警，并用宿主模板回一句"我这边工具面不对，已停"。
- 服务启动后对全部存量桌子做一次同样的自检，不通过就不启用该桌。

这比"相信热更会正确补装"便宜，也比出事后再查便宜。

## 租约与第二个声音

同库：单行 `lease`，心跳 15 秒，过期 60 秒；抢到才能发；抢不到则只判断不发送（等价 shadow），日志报警，`status` 显示持有者。

跨机：同库租约挡不住另一台机器上同一个飞书应用的实例（F34：Hermes 在 Linux 上跑过 15 天，一条消息收到 8 个回复）。处置是发现而不是防止：

- 每次 reply 档出站后 30 秒，读一次该会话最近消息，统计本应用发出的、回复同一条入站的条数；
- 大于本库 `outbox` 记录的条数 → 判定有第二个实例，打断老板一次并在 `status` 标红；
- 防止只能靠运维：一个飞书应用只给一台机器的凭据。

所需读消息历史的权限与接口是否已开，是待验证项 P6。

## 失败隔离（一个模块坏了，系统还能做什么）

| 坏在哪 | 还能做什么 | 不能做什么 |
| --- | --- | --- |
| 桌子（模型侧） | 内核继续 tick、快路径继续处置（停止词、序号、寒暄、直通）、执行体继续跑、出站继续 | 不能做新判断；新消息只能走快路径或排队 |
| 判断（工具实现） | 桌子能起回合但工具报错；内核仍记账 | 不能开新承诺；已有承诺继续由执行体推进 |
| 执行体 | 判断仍能受理并排队；承诺标 queued | 不能派新活；已有尝试若会话还在则保持 |
| 时机与措辞 | 交付仍能说话（模板兜底） | 不能主动预警、不能发简报、额度不生效 |
| 记忆 | 判断仍能跑（案卷少两段） | 不能用历史偏好与判例；跨桌连续性退化 |
| 规则 | 用最后一份通过校验的规则快照 | 不能自迭代；新规则不生效 |
| 世界模型 | 已解析的路径与授权缓存仍可用 | 不能注册新实体、不能做新归属 |
| 内核 | 全系统停止写入 | 只剩只读命令与告警 |
| 飞书发送 | 出站排队重试 24 小时 | 不能对外说话；恢复后补发或附"有一条没发出去" |

## 降级矩阵

| 情况 | 系统行为 | 对外表现 |
| --- | --- | --- |
| 模型不可用 | 快路径继续；判断回合失败重试一次，再失败用宿主模板 | "这条我没处理好，请再说一次" |
| 发送持续失败 | 出站标 failed，24 小时放弃 | 下一条消息末尾附"有一条没发出去" |
| SQLite 锁死 | 只读模式：不写账本，不判断，只应答已知状态 | `status` 可查；新消息排队 |
| 租约被别的进程持有 | 只判断不发送 | 无（日志与 status 标红） |
| 第二个实例在发 | 打断一次并标红 | 老板收到一次提醒 |
| 热更后工具面不对 | fail-closed，本回合不跑 | "工具面不对，已停" |
| 磁盘/目录异常 | 停止派新的 durable 活 | 简报一行 |

原则：**降级只减少能力，不制造错误**。任何"不确定"的路径都选择闭嘴或排队，而不是猜着做。

## 第 0 天必须先测的五件事

对应需求基线 P1–P5。任何一条不成立就改设计再写代码：

1. 桌子会话的工具面能否真的只剩桌面工具（restrict + guard，需要先拿到 agent 级 ctx，F30；P5、R2 的前提）。
2. 预设白名单与模型参数：能否按预设起执行体、provider/model/effort 实际可用集合（P1、P2；R10 的前提）。
3. 飞书原始事件回填 union_id 后，四类身份判定是否稳定（F17；G6 的前提）。
4. 会话事件里能否读到回合结束原因与 token（F2；P4、G1/G4 的前提）。
5. 运行中的执行体会话能否被送入新输入而不打断当前回合；空闲会话 `prompt(queue)` 能否起新回合（P4、F1；G3、R19 的前提）。

## 契约

```
startup() → { leaseHeld, reconciled, degraded[] }
reconcile(now) → { orphaned, closed, healed }      // 每轮 tick 都调用
selfCheck(deskId) → 'ok' | 'fail-closed'
secondVoice() → { detected, expected, observed }
degrade(reason, scope) → degrade_id                 // 写一行 degrade_event（原因、范围、起止）；status 的降级段只从它读
```

## 依赖方向

依赖协议、内核（只读加修复写入）、桌子（读会话状态）、执行体（对账与清扫）、世界模型（落点）。被观测与命令读取。恢复模块不做判断、不发消息；它要说话时只写一条告警出站提案，经内核出口。

## 失败模式

| 失败 | 表现 | 处置 |
| --- | --- | --- |
| 对账漏掉 | 承诺卡 running，名额被占满 | tick 拉式对账，不依赖启动；名额是唯一索引，卡住会立刻在读数里显现 |
| 双实例 | 一条消息多个回复 | 出站后计数探测；发现即打断一次 |
| 热更后工具面退化 | 桌子能执行命令 | fail-closed 自检：可见工具集不等于桌面工具集就不跑 |
| 对账误杀 | 把正在跑的会话标成孤儿 | 只标不杀；先 inspect 再判定；标孤儿后等下一轮复核 |
| 降级不可见 | 老板以为它坏了 | 每次降级写一行 `degrade_event`，`status` 与简报从它读；降级矩阵是产品的一部分 |

## 读数

```sql
SELECT commitment_id, state FROM commitment WHERE state IN ('proposed','open','at_risk') ORDER BY 1;
SELECT commitment_id, count(*) FROM outbox WHERE idem_key LIKE 'orphan:%' GROUP BY 1 HAVING count(*)>1; -- 空
SELECT count(*) FROM commitment WHERE state='orphaned' AND closed_at IS NULL;                          -- 0
SELECT name, holder, epoch, heartbeat_at FROM lease;                                                  -- 单行
SELECT count(*) FROM attempt WHERE state='running' AND cancel_origin='reconcile';                      -- 只增不异常
SELECT degrade_id, reason, scope, started_at, ended_at FROM degrade_event WHERE ended_at IS NULL;      -- status 降级段
```

重启前后各跑一次"在办集合"查询，diff 必须为空；每件至多一条孤儿通知。

七步链的机械检查由 `scripts/superagent-check.mjs` 承担（只读账本，退出码 0 成功、1 失败、3 无数据），维护者归本模块；它就是需求基线七步链第 7 步的落点。手跑 SQL 只用于定位，不用于验收。

## 扩展点

- 对账检查项：`recovery/checks/<name>.ts` 实现 `check(now) → Finding[]`，注册一行；只读账本与会话状态，修复动作只能经内核的修复写入。
- 降级策略：配置（哪些情况进哪一档），不是代码分支。
- 不做"自动重写账本"：修复只允许追加 journal 与状态迁移，不允许回滚已发生的事实。
