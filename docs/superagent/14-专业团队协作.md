# 专业团队协作：秘书组织，专业角色负责，证据验收

职责：定义软件工程的专业责任、协作方式、交付物和角色验收。本文是目标设计，不代表已部署团队或已验证专业能力。跨模块对象归 [协议](02-协议.md)，秘书组织与纠偏归 [托管协调](12-托管协调.md)，结案和系统级测试归 [验收与评估](13-验收与评估.md)。

## 组织原则与方案取舍

采用一个面向老板、跨项目承担结果责任的秘书，按目标和风险组建专业团队。专业责任持续存在，Agent 会话按需运行；角色不是模型名称、固定进程、组织头衔或新的运行时实体。临时团队可跨多个项目与机器，同一项目也可服务多个目标。长期项目知识依靠版本化资料与原生线程接续，不靠每个项目常驻一个经理。

| 方案 | 收益与代价 | 选择 |
| --- | --- | --- |
| 秘书、实施者、末端评审三类 | 调度简单，但容易遗漏产品、架构、体验与运行责任；末端评审难以补救方向性缺口 | 不作为专业软件交付的完整组织 |
| 固定复制人类部门和逐级审批 | 专业名称齐全，但无差别开角色增加传话、上下文损失和等待；头衔不能证明能力 | 不采用固定人数与审批层级 |
| 按专业责任组队，按风险决定独立性与介入时点 | 专业责任明确，低风险可合并；需要角色能力验证、清晰交接和独立验收 | 采用 |

秘书负责用户意图、跨项目优先级、责任覆盖、资源与进度、纠偏、回收和对外承诺。专业角色负责本领域判断及可验证交付，不能只给建议便结束责任。秘书可以质疑结论、要求补证、调整方法和更换人员；不能凭行政地位替代专业证据或把失败改成通过。确定性状态、权限、计时、资源互斥和版本检查由宿主承担。

## 专业责任与交付验收

下表是所有软件事项都要检查的责任覆盖表，不要求每次创建八个 Agent。每项责任在团队分工中标记适用、由谁覆盖、需要独立检查的范围；不适用必须说明基于什么事实。产物可以是有来源的简短记录，不能用文档页数或模板齐全证明专业性。

| 专业角色 | 负责的判断与协作 | 必需交付物（按适用范围） | 角色验收与明确边界 |
| --- | --- | --- | --- |
| 产品与业务分析 | 从老板目标推导用户场景、业务规则、异常路径和优先级；与体验、架构、质量核对可行性和遗漏 | 场景与业务规则、需求到验收项映射、假设及来源、实质待决点 | 关键用户目标和异常有可观察结果；不得用技术指标替换原问题、擅自删需求；真实产品取舍由秘书准备后请老板决定 |
| 架构与技术负责人 | 系统边界、数据与接口、兼容迁移、非功能要求、跨项目组合；组织关键风险实验，回答实现问题 | 技术决策与理由、接口/数据契约、风险与验证方案、迁移/恢复设计、整合约束 | 关键假设有实测或明确未证实项；满足项目约束与目标负载；高风险架构由独立技术审查验证，不能自证所有取舍正确 |
| 交互与体验设计 | 用户流程、信息层次、操作反馈、错误恢复与可访问性；与产品、实现、质量持续协作 | 流程或原型、正常/空/加载/错误/权限等适用状态、响应式与体验判据 | 用户能经真实入口完成场景并恢复常见错误；不能仅交一张好看的图；只有确需老板个人习惯的主观项才等本人 |
| 交付推进 | 分解依赖、安排检查点与资源、组织整合、管理阻塞；简单事项由秘书兼任，复杂目标可独立委派 | 版本化分工、依赖与写域安排、整合计划、风险与恢复记录、阶段成果清单 | 无无人负责的依赖和等待；整合及返工能闭环；不能以任务数或进度百分比自签质量，也不能另建账外队列 |
| 工程实现 | 按需求和技术契约实现、调试、开发者测试、可维护性改进；及时反馈设计缺口 | 精确代码/构建版本、开发者测试、必要文档与使用说明、已知限制、交接材料 | 行为符合合同和项目门禁，修复有能检出旧错误的验证；不能替代独立验收，不能修改要求或弱化检查来过关 |
| 测试与质量工程 | 从需求阶段设计验证，审查可测试性，独立复现、端到端/回归/整体验证；对证据充分性负责 | 验证设计、独立测试资产、候选环境与执行证据、逐项结论、缺陷及解除条件 | 覆盖合同风险、真实场景与异常；能拒绝已知坏产物且不误拒正确产物；不在被审实现上自行修复后自签，拒绝也须有依据 |
| 安全、性能等专项 | 权限/数据/威胁、并发/负载/资源、领域合规等实际专项风险；与架构、质量、运行协作 | 威胁或负载模型、专项实验与原始证据、风险分级、修复及复查结论 | 验证适用环境、权限边界和负载假设；不能用通用清单冒充测量；必要专项能力缺失保持未验证，由秘书补齐 |
| 发布与运行维护 | 可重复交付、配置与迁移、回滚或补救、监控及观察期、事故处置；在设计期反馈运行约束 | 版本化发布包、前置检查、操作/补救方案、目标授权引用、交付回执与效果证据、运行交接 | 精确候选和目标可追溯、失败可发现和处置；获对应授权后执行；部署成功不等于效果通过，不以上线结束责任 |

工程实现可按前端、后端、数据、基础设施等写域与能力拆分；专项可按风险拆分。每项仍有唯一主要负责人和明确消费者，不因增加角色把接口责任留空。专业角色可以提出调查、补证或跨角色协作请求，不能自行转授权限；秘书或受委派的交付推进者将请求纳入同一账本调度。

## 按风险组队与能力边界

受理后先由产品、技术和质量责任共同检查目标与风险，未知风险先安排有界调查或实验。所有适用责任必须有负责人，随后才开展依赖这些结论的工作；不要求等所有文档齐备才做可逆原型或互不依赖的工作。

| 工作形态 | 可采用的组织 | 不可省略的责任 |
| --- | --- | --- |
| 低风险文案或已有边界内的小修复 | 秘书兼交付推进；同一专业执行者可兼产品澄清与技术分析；独立机械判据足够时不另开质量 Agent | 场景、适用风险、交付位置和判据有据可查；超出机械覆盖的语义判断仍需独立验证 |
| 用户可见功能或跨层改动 | 产品、技术、体验、质量责任从设计期介入；实现按写域拆分，可合并低冲突角色 | 真实流程、异常状态、接口契约、独立质量结论和整合责任 |
| 权限、敏感数据、不可逆迁移、生产可靠性或跨项目接口 | 明确专项负责人、独立领域复核和运行负责人；复杂依赖委派交付推进 | 关键风险实验、迁移/补救、组合验证和发布前置；不能由同一执行上下文完成关键方案及独立背书 |

合并的是执行席位，不是责任。角色分工必须记录兼任关系与独立性冲突；亲自生成或修改被验收产物的席位不能做它的最终独立评审。正常返工复用各自原生线程，新增独立评审使用独立上下文。简单更换模型名字、在同一线程换提示词或让另一 Agent 复述实施者结论，都不构成独立验证。不同模型可降低部分相关偏差，但不能替代独立证据。

每个角色 profile 必须绑定适用任务、知识来源、工具与环境、代表性能力评估、已知限制及有效版本。专业性要靠目标领域样例和真实任务证据：体验角色需实际浏览器与可视检查，性能角色需负载与剖析工具，质量角色需独立测试环境，架构角色需实际接口与系统事实。模板完整、模型自称专家和一次成功均不足以证明能力。

质量角色的独立性还包括 [验证执行隔离](10-执行体.md#验证执行隔离)：准备测试的权限不直接交给被测代码，独立环境不等于可信判据。质量/专项发现方法失信时负责专业核查及替代验证，秘书按 [资格失效协议](02-协议.md#专业分工与审查记录) 追踪受影响事项，不能只换一个角色继续使用旧通过。

缺专业能力时秘书先安排授权内的调查、工具修复、其他已验证执行端或能力建设事项；未验证的新组合只能承担适配范围内工作。确实缺少可用能力时保留未完成状态与复查，不把专业判断交给老板或用较弱方法冒充同等证据。无法完成的终态须满足 [诊断与自主恢复](12-托管协调.md#诊断与自主恢复)。

## 协作方式与交接责任

1. 秘书保留原始目标，组织产品、技术、体验和质量建立当前合同、风险与分工。技术数值须由用户场景、运行基线和项目规则推导，说明依据；不把「生产级」留成口号，也不替老板改变使用场景或质量承诺。
2. 各专业并行调查并相互挑战。发现设计不可行或验收盲点时先修订方案和验证设计；已有目标内的工程细化自主决定，影响目标、承诺或权限的取舍才由秘书送用户裁定。
3. 交付推进者建立依赖和尽早可验证的整合切片。实现者边做边反馈，质量与专项持续验证；专业审查按风险和产物变化触发，不是每个角色逐级批准的串行瀑布。
4. 交接包包含当前需求/合同/技术决定、精确产物版本、适用约束、已知缺陷、未决假设、必需验证、失败方法、材料与消费方。消费者确认能用或指出具体缺口；送出材料不代表责任转移成功，原负责人继续补齐。
5. 消费确认只表示材料进入工作，不表示交付物被验收。专业判断、缺陷和澄清进入同一版本化记录；短讨论可通过受控角色通信进行，影响合同、安排或验收的结论必须归账，不能依赖私聊或老板传话。
6. 候选成果在精确版本上做独立专业检查与整体验收。质量角色可以提出失败或证据不足；秘书安排原责任角色返工并跟踪输入消费，由原评审线程复核新候选。父目标按当前项目组合判断，不按各角色报告通过求和。
7. 发布角色准备证据及恢复能力，秘书把准备充分的发布申请交老板；按 [发布授权协议](02-协议.md#发布授权) 执行。授权后技术操作、观察、事故诊断和授权内补救仍由团队承担。
8. 阶段成果满足其合同即可向老板汇报，但只在整个事项的必需验收和约定交付完成后结案。长期职责持续观察，并将复发交回对应专业责任处理。

## 验收争议与专业裁决

质量发现必须绑定原要求或有依据的工程风险、候选版本、复现证据、影响及可验证解除条件。实现者可以提出反证，不能自己关掉缺陷；评审者不能以个人喜好、不断增加无关标准或无限补测阻塞交付。

普通分歧先由原责任角色复现和补证；未解决的技术争议由秘书安排未参与争议产物生成的领域复核者裁决，必要时组织对照实验。内部专业裁决写入 `professional_decision`，不是伪造老板的 `decision`。原评审结论保留，只有复核证据才能撤销误报或形成替代结论；秘书不能为赶交付直接覆盖失败。复核者也缺证据则为 inconclusive，转补证、换方法或有条件等待，不能靠多数投票判通过。

新发现的工程细化或测试缺口可以自主补进当前验收合同，绑定新版本并记录影响；涉及削减真实用户要求、降低项目硬标准、变更目标或对外承诺，不能借技术裁决绕过用户与适用约束。若系统把业务规则错误推导成了必需验收项，由无相关生成冲突的专业复核者按 [判据来源与修正协议](02-协议.md#专业分工与审查记录) 证明错误、修正版本并重新验证；这不要求老板替系统纠正技术判据，也不允许把无法达标伪装成误派生。实质产品取舍由秘书整理收益、代价、证据与推荐集中请老板决定；技术争议本身不是升级给老板的理由。

## 一个贯穿示例：跨项目批量导入

目标是让用户可靠导入数据，涉及前端项目和数据服务项目。产品负责人明确重复导入、部分失败和撤销的业务语义；体验负责人设计预览、错误定位和重试流程；技术负责人确认幂等、事务/异步处理、接口版本与迁移；质量负责人先从这些场景设计验证，安全/性能按数据和负载风险介入，运行角色准备迁移、观察和补救。

前后端实现分别通过测试仍不能结案：质量必须运行对应版本组合，验证断线重试、部分失败、权限隔离和结果可核对。若实现通过删掉失败行来让成功率变高，秘书按原目标识别指标替代并阻止交付，派产品和质量明确反例，再交原实现线程修复。若测试误把符合业务规则的重复记录判错，走内部复核纠正判据，不请老板调试测试。若重复数据究竟合并还是拒绝会改变老板业务意图，先调查已有规则，确无依据时才集中请求产品裁定。

本例仅说明协作方式，不为所有项目强加批量导入功能或同一性能阈值。角色能力、独立性、争议处理和无人催办的完整验证归 [验收与评估](13-验收与评估.md)。
