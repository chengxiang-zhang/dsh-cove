# 协议：责任、会话、操作与验收

职责：定义跨模块逻辑对象、状态和操作约束。本文是目标协议，尚未迁移到当前 DDL；实现时必须版本化迁移，不得直接把本文字段当作现存数据库列查询。

边界：协议规定可表达什么和什么迁移合法，不把语义判断或具体阈值写成表约束。现有 `inbox_events`、`reply_jobs` 与 `sa_` 表的兼容由迁移负责，插件不能临时改变公共契约。

## 身份与对象

| 对象 | 核心内容 | 归属 |
| --- | --- | --- |
| `party` | 可信用户、Agent 与服务身份；人的稳定主键与通道身份映射 | 世界模型 |
| `project` | 稳定项目 id、别名、目标、约束、仓库和环境引用 | 世界模型 |
| `workspace` | project、host、规范路径、checkout/branch、资源锁、交付目标 | 世界模型 |
| `responsibility` | 长期职责、项目集合、期望状态、观察源、授权引用、复查策略、状态 | 托管协调 |
| `commitment` | 有终点事项、原始意图、项目集合、职责来源、验收与交付合同、版本、状态 | 托管协调 |
| `dependency` | 事项之间的前置或共享资源依赖；满足条件与版本 | 托管协调 |
| `decomposition_edge` | 父子事项、父需求与裁定版本、子合同版本、必需性、成果要求与有效状态 | 托管协调 |
| `finding` | 来源、事实时间、证据、影响、去重键、处理结论、关联事项 | 托管协调 |
| `session_binding` | host/provider/session_id、项目与工作区、观察游标、控制模式、能力快照 | 执行体 |
| `attempt` | 事项中的一次分工；角色、会话绑定、交办版本、预算、结果与结束原因 | 执行体 |
| `executor_request` | 执行端反向请求的原生身份、请求内容、所属版本、待答状态、响应与解除证据 | 执行体、托管协调 |
| `coordination_action` | 一次协调操作的目标、意图、预期版本、权限、幂等键与远端回执 | 内核 |
| `control_lease` | 某会话当前控制者、epoch、期限、来源；与消息出口租约分离 | 内核 |
| `delivery_step` | 合同版本、目标、产物 revision、整合/提交/推送/发布动作、前置条件、回执和补偿边界 | 托管协调、验收 |
| `control_intent` | 暂停/恢复/停止/接管的范围、来源、epoch、在途处置与持久回执 | 内核 |
| `evaluation` | 验收合同版本、产物版本、证据引用、检查者、逐项结论与交付确认 | 验收 |
| `preview_candidate` | 候选产物集合、需求版本、体验环境版本、访问范围、准备回执与有效性 | 验收、托管协调 |
| `decision` | 事项、待决范围、方案版本、证据、建议、缺省动作及用户裁定回执 | 托管协调 |
| `intake` | 入站唯一处置；允许定位多个事项但不得重复认领 | 内核、判断 |
| `desk` / `deliberation` | 对话、实际受众、事实版本、判断输入与结果、会话代次 | 桌子 |
| `journal` / `outbox` / `lease` | 追加事件、对人发送意图、唯一出口租约 | 内核 |
| `memory` / `rule` | 来源与可见域明确的运行上下文引用、硬策略或学习候选 | 记忆、规则 |
| `mandate` | 主体、目标、能力、条件、授权来源、版本、有效性与撤销 | 世界模型 |
| `doc_index` / `degrade_event` | 有来源的交接与证据定位；能力退化范围和恢复条件 | 记忆、恢复 |

`session_id` 只在 `(host, provider)` 命名空间内唯一。项目与会话多对多关系通过事项和分工表达，不能把同名仓库当同一工作区。线程是对话线索，不是任务唯一约束。

## 长期职责与事项

`Responsibility` 必含 `id, intent, project_refs[], desired_state, observation_sources[], mandate_refs[], review_policy, status, revision`。状态 `active | paused | revoked`；事项完成后职责仍可 active。没有值得处理的信号时正常保持观察，不编造任务。

`Commitment` 必含 `id, intent, source_refs[], project_refs[], responsibility_id?, parent_id?, requirement_revision, acceptance_contract, delivery_contract, boundary, accountable, next_review_at, state, control_state`。`accountable` 指向 Superagent 的责任主体，`assignee` 在尝试中；不能因换执行体把责任转给老板。

事项状态与迁移：

```text
proposed → ready → working → verifying → delivering → fulfilled
                 ↘ waiting / at_risk ↗
未终态 → released（用户停止） / withdrawn（未承接或被撤回）
未终态 → broken（已证明在当前约束下无法完成，并保存原因与现场）
```

- `proposed`：尚未完成意图、授权或受理判定；授权内职责产生的事项可直接 ready。
- `waiting`：外部依赖、资源或用户裁定等待，必须有等待对象、恢复触发、最晚复查和恢复阶段。只阻塞依赖该条件的工作。
- `at_risk`：需要诊断或换策略，责任仍在系统，不隐含需要用户选择。
- `verifying` 检查下一交付步骤的前置验收，不通过回 working；`delivering` 包含逐步交付与交付后效果检查，等待观察时记录恢复阶段。需要修复时可回 working，但保留已发生交付事实。未完成必需验收或约定交付不能 fulfilled。
- 终态不改写。结案后的新增需求建立有前情链接的新事项；未结案事项的追加递增需求版本，使旧验收失效，部分交付后的追加按交付操作对账。
- `parent_id` 只表达目标拆解，不由同线程、不同发送者自动推导。

方向型委托可以在 `proposed` 下安排已有授权覆盖的调查和方案分工。调查后无实质待决项且已有授权覆盖时，由系统记录判断依据，确定需求版本、验收和交付合同及授权引用，直接转 ready 并派发；不制造用户采纳记录。需要用户采纳方案时，`decision` 绑定事项、待决范围及方案版本；裁定须来自可信用户并匹配当前版本，只阻塞依赖该裁定的分工。采纳结果写回合同后解除相应等待；拒绝则保留原目标并重新组织方案，不默认取消目标。方案采纳不授予合同以外的权限；新证据改变待决方案时，旧裁定不能用于新版本。

控制状态与进度状态正交：`control_state = autonomous | paused | human_controlled`。暂停保存原进度阶段、输入和成果；恢复重新核对权限、现场与版本，再回该阶段。released 是用户明确取消事项的终态，不通过 resume 复活；再做要有新的用户委托或职责范围变更依据。

职责 pause 的默认效果是停止发起新事项，并暂停其专属在途事项；同时被独立委托的共享事项保持自身控制状态。职责 revoke 撤销该职责提供的后续操作依据，保留已发生事实。暂停后在途处理采用可中断的安全检查点；明确 stop/cancel 走即时取消路径。无法唯一确定共享归属时不扩大停止范围，保留控制意图并请求一个范围裁定。

## 目标拆解与整体验收

`parent_id` 表示主要拆解归属，`decomposition_edge` 保存父需求 revision、裁定引用（无需用户裁定时为空并附自主判断依据）、子事项及合同 revision、required、所需成果和验收映射。复用其他事项成果通过带版本的 dependency 表达，不靠改写其父归属夺取控制。拆解与依赖均不得成环；必需性来自父合同，不得为结案把失败子单改成可选。

父需求或裁定版本变化时，账本事务同时更新父版本并使旧拆解绑定失效。子事项的 Action 必须校验自身和所依赖的祖先/拆解版本，不能只验证子单未变。托管协调根据影响证据为不受影响的分工重新绑定当前版本；受影响或影响未知的分工停止新的旧版本动作，修订合同与交办后再恢复。已在途写入按控制 epoch 和目标端围栏停止或隔离后对账，未确认前不派替代写者。失效的是旧证据对当前目标的适用性，已发生操作、旧产物和终态子单不改写；需要返工的终态子单建立关联修订事项。独立于本父目标的工作继续。

父事项验收冻结当前目标对应的成果清单：必需子单及合同版本、精确产物 revision、接口/环境组合、依赖满足证据和逐目标交付要求。各子单通过只是输入；父项还要验证组合兼容与总目标，不能按完成数求和置 fulfilled。复用旧成果须有对当前合同仍适用的验证；任一必需成果或需求变化使相关组合结论失效。父项结案同时需要这份清单的整体验收和约定交付证据。

子单的候选成果可进入父组合验收，不要求子单先 fulfilled。父合同要求组合通过才能执行的交付步骤，必须把父组合验收列为前置；允许独立交付的步骤按其合同推进。交付后的整体效果在对应观察阶段验收，不能让「子单先结案」和「父项先验收」互相等待。

## 分工与执行尝试

一个事项可有多个角色尝试（调查、实施、评审、验证、临时协调），共享写域必须互斥。`attempt.state = pending | running | ended`；结束原因保留宿主原值并归类，不设置「编号最多 3」的协议上限。

`attempt` 保存 `binding_id, role, assignment_revision, prompt_ref, provider/model/effort, cwd, host, branch, budget, progress_refs, end_reason, cancel_origin`。预算约束单次尝试，不自动终止事项。`cancel_origin` 保留 release/budget/deadline/stall/loop/dispatch/reconcile/external 的可区分语义；外部取消必须暂停自主控制并查明权属，不能直接自动拉起。

输入使用唯一 `request_id`，分别记录 `submitted, accepted, consumed, unknown` 及消费回合。最低消费证据来自宿主或可信适配器：`(request_id, assignment_revision, payload_digest, session_identity, turn_id)` 被写入该回合实际输入记录，并有该回合开始处理的事件。HTTP 接受、排队成功或模型自称「已理解」不够；开始处理也不等于完成，成果仍由验收检查。

重试沿用 request_id；更换执行体时创建关联原输入的交接输入及新回合证据，记录 superseded_by，不能伪造旧执行体已消费。无法证明消费的适配器不能承担要求可靠续聊的角色；可以选择另一已验证执行端，在核实旧尝试停止后交接。若没有可用端，报告能力缺口并进入有复查条件的等待，禁止靠无限 unknown 假装推进。

评审退回、CI 失败和需求补充经账本转成有来源的协调输入，绑定事项、目标角色绑定、需求版本、被审产物版本（如适用）及证据。评审发现只改变工作与验收状态；需求变更才递增需求版本。正常返工保持原执行者的原生会话绑定；有连续复核任务的评审角色也复用原绑定。显式更换执行体走交接，不能将新会话标成原会话已恢复。

## 执行端反向请求

执行体需要回答、工具审批或外部交互时，适配器将原生请求归一为 `executor_request`，先入账再唤醒协调。记录逻辑 id、binding、原生 request/turn/item 身份（按 provider 能力）、连接或服务代次、原始类型与载荷摘要/引用、事项及交办/需求版本、控制 epoch、原生有效期、等待对象、最晚复查、响应 Action 与解除证据。原生 request id 按其实际命名空间去重，不能假定跨连接唯一；它与秘书发送输入的 request_id 分开。

状态为 `pending → responding → resolved`，失效为 expired，结果不明为 unknown；resolved 必须带已回答、拒绝或被原生端清除等原因。原生端解除请求不等于答案已使用、工具已执行或任务完成，须继续核对对应回合、工具及成果证据。模型输出的疑问可形成待处理事实，但不能伪造一条原生审批请求。

协调者自行补上下文、调查并回答授权内的技术问题。审批按请求的真实动作、目标、权限范围与现有 mandate 求值；只在原生协议允许代理处理且授权足够时响应，原生许可的作用域与期限不得超出该 mandate，会话级许可仍须能随授权撤销，不因一次审批建立永久许可规则。实质产品取舍、缺少授权或原生机制要求本人完成的操作才形成准备充分的用户待办，保持与原请求的关联；用户沉默或超时不构成许可。其他可独立分工继续，不把待答误诊为空跑。

响应使用受控 `respond_request` Action，绑定原请求、当前版本、控制 epoch、响应内容及授权依据，发送前确认该请求仍活跃且内容未变。丢回执先对账，不换 id 盲答。重连后只在核实原请求仍有效时回复；被结束、取消、其他客户端处理或重启清除的请求不得重放，未解决的问题仍由秘书负责，按 [执行体](10-执行体.md#codex-app-server-适配) 在原线程重新衔接。无法确认有效性时保留 unknown 和有界诊断/复查，不能无限挂起或退回让老板传话。

## 协调操作与副作用

```text
Action {
  id, idem_key, kind, target_ref, commitment_id?, responsibility_id?,
  expected_revision, scope_revision_refs[], expected_epoch, mandate_ref, payload_ref,
  expected_observation, state, receipt_ref?, error?
}
state: planned → authorized → sent → confirmed | failed | unknown
```

发送前持久化意图；发送前再次核验授权、控制租约和事实版本。发生超时但可能已执行时进入 unknown，读取远端事实后再决定重试，不能换幂等键盲发。确认完成需要可观察回执；模型自述不是远端回执。

`scope_revision_refs` 保存影响该动作的父目标、拆解绑定和依赖版本；顶层独立动作可为空。远端执行信封和后续工具许可遵循这些约束的撤销结果，不能只在队列入账时验证一次。

停止先提升控制 epoch、撤销后续写操作，再取消在途执行并核实。失联时记录 `stop_pending` 控制意图，不谎报停止，不因此释放仍可能被远端占用的资源锁。

## 候选体验与用户验收

`verifying` 可安排受控 `prepare_preview`，由获授权的执行角色或注册端口准备候选环境；不要求先完成正式交付。`preview_candidate` 绑定事项/合同与需求 revision、精确产物集合、目标环境及其部署/配置版本、访问方式、可见受众、授权、准备 Action 和有效期。状态 preparing/available/expired/retired；available 要有环境实际运行该候选版本且用户可访问的证据。可变 URL 不能单独充当版本身份，环境被覆盖或访问失效时停止使用旧候选作为当前体验证据。

预览中的仓库、工作区和环境准备复用 provision/integrate 等受控步骤，按真实副作用求值授权。预览权限不授予生产发布或公开暴露权限；没有预览目标授权时先准备可审阅方案，等待仅限该依赖。已有本地或受限环境足以体验时自行使用，不为常规体验另造审批。

本人体验反馈进入 evaluation，记录可信 party、来源消息、验收项、候选和合同/需求版本、通过/拒绝/需澄清及理由。含糊反馈先结合明确候选归位，无法唯一定位才澄清；沉默不通过。拒绝使受影响分工回 working，相关体验项等待新候选；需求、产物或影响体验的环境变化使相关结论失效，客观且未受影响的证据可经核对复用。本人体验确认是对应正式交付步骤的前置验收；该步骤前置条件通过后可进入 delivering，候选可访问不等于已经正式交付。

## 交付操作

交付合同展开为 delivery_step，每步绑定目标、产物 revision、需求 revision、前置步骤、授权和可观察回执。受限执行体完成准备与本地整合；宿主通过结构化 provision/integrate/deliver 操作安排相应执行角色或已注册交付端口，不向协调座席开放任意 shell。

验收合同将每个必需项绑定到交付步骤的前置验收或交付后效果验收，并记录证据依赖、观察条件和最晚复查；步骤与验收依赖不能成环。前置验收通过且授权有效即可执行该步骤，不等待只能在交付后获得的证据。已交付但效果尚待观察时保持 delivering 或带恢复阶段的 waiting，持续检查；所有必需项与约定交付证据满足后才能 fulfilled，不能把合同要求的效果改为可选后续任务来提前结案。

项目初始化沿用受控 `provision`，目标须注明是项目登记、仓库、工作区还是初始化阶段，并按阶段记录独立 Action 和回执。相同的工作区路径不构成相同项目或仓库的证明。阶段的目标与授权见 [世界模型](04-世界模型.md)。

单步只有 pending/running/confirmed/failed/unknown；目标交付凭据由验收核对。多个目标不是分布式原子事务：一处成功、一处失败时保留每步事实，事项继续 delivering/at_risk，不重放已确认步骤、不宣布整体完成。

交付中收到追加，先阻止尚未发送的旧版本步骤；已发送的只对账，不能假定撤销成功。已发生交付保留旧版本事实，新需求使当前验收失效，形成后续修订并按新版本继续；补偿或回滚也是有边界的独立交付步骤，不能擅自回滚不可逆外部动作。

## 工具契约

以下是逻辑工具能力，具体工具命名与 JSON Schema 在实施协议版本中固化。上下文身份和权限由宿主注入，不接受模型自报。所有变更经账本事务与 Action 执行。

| 能力 | 输入与输出 | 边界 |
| --- | --- | --- |
| `look` | 项目、职责、事项、文档、会话的引用与分页查询 → 有来源的快照 | 受众与用途过滤，限制返回体量 |
| `judge` | 事件、事项关联、解释与处置 → 处置记录 | 不直接执行副作用 |
| `commit` / `amend` | 意图、项目、合同、前情 → 事项及新版本 | 不偷偷修改交付范围 |
| `plan` | 分工、依赖、资源、检查点 → 版本化安排 | 同时验证无环与写域冲突 |
| `operate` | inspect/dispatch/attach/send_input/steer/respond_request/cancel/collect/provision/integrate/prepare_preview/deliver + 目标与预期事实 → action id | 只允许注册的协调动作，无任意 shell |
| `verify` | 事项、合同及候选产物 → 验收请求 | 不能由实施者直接置通过 |
| `release` | 明确对象与停止范围 → 控制意图、确认状态、保留成果 | 歧义时不能猜测停止其他事项 |
| `remember` / `learn` | 有来源的经验或方法候选 → 引用、评估状态 | 不产生授权，不直接改可移植技能文件 |
| `say` | 对人消息提案、受众、依据 → outbox | 唯一出口与披露检查 |

错误至少区分 `NOT_AUTHORIZED, STALE_REVISION, CONTROL_LOST, CAPABILITY_MISSING, TARGET_AMBIGUOUS, INPUT_UNCONFIRMED, WRITE_CONFLICT, EVIDENCE_MISSING, DISCLOSE_BLOCKED`。技术错误交系统诊断，不能把工具错误直接转成老板待办。

执行体 `report` 保存 progress/ready/blocked/failed、产物引用、证据与问题。blocked 可以是技术障碍，无需构造给老板的问题；ready 只触发验收。

## 消息、记忆与事件

outbox 保存消息幂等键、来源事件或事项版本、moment、受众快照和租约 epoch。一条入站只生成一次语义答复；之后的交付、授权请求是独立生命周期事件，不能被「已经 ack」永久挡住。单条传输长度服从通道限制，通知篇幅由策略控制，不把所有文本 CHECK 到 100 词。

记忆冲突键至少含主体、话题与作用域；用途可见性与发言可见性分开。知识版本与授权版本不是同一对象。私聊材料进入 Agent 提示词同样属于披露，需要目的与访问范围校验。

事件包括 inbound、observation、executor_report、executor_request、action_receipt、evaluation_result、tick、authority_changed、human_takeover。原生请求的提出、变化和解除均有来源事件。事件先幂等入账，再请求协调；原始大体量日志保留外部引用和游标，不全量复制到每个模型回合。

通道仍实现 inbound/send/react/audience/history；现有配置命名空间和平台凭据归属不因逻辑协议改写而改变。

## 不变量与失败处理

- P1 只有内核打开运行账本写事务；可移植知识由 OpenViking 持有权威，账本只保存引用和运行事件。
- P2 journal 只追加，更正带 supersedes；终态证据不可偷偷替换。
- P3 事件、操作和消息各有幂等键；会话绑定按宿主命名空间唯一；重放不重复副作用。
- P4 每个非终态事项与 active 职责都有下一次复查或有效订阅；等待也必须可唤醒。
- P5 每个外部写操作有有效授权及控制权；人接管或撤销使旧 epoch 操作失效。委派后的真实工具与子进程同样受目标端执行围栏约束，机制归 [执行体](10-执行体.md)。
- P6 fulfilled 必须绑定当前合同、当前产物的验收和交付证据；没有证据就保持未完成。
- P7 私聊、项目与群材料的权限按实际接收者计算，不能只用粗受众类别。

迁移必须检查旧数据映射、原始证据保留与回退可读性。未知协议版本拒绝变更并保留原始载荷；不得把不理解的状态当成功。旧 `unverified/orphaned` 记录保留事实，但不能无证据迁成 fulfilled；映射到待核查的 at_risk/waiting 需要诊断记录。

## 依赖、扩展与验证

协议无运行模块依赖。新对象、状态或工具能力需要显式协议版本与迁移；适配器只注册约定能力，不自创状态语义。

验证重点：状态迁移、版本失效、幂等、权限撤销、控制租约、输入消费、验收与交付绑定。此处不提供针对尚未实现字段的伪 SQL；实测规范归 [验收与评估](13-验收与评估.md)。
