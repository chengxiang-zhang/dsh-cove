# 内核：持久事实与受控操作

职责：保证认领、账本事务、唤醒、协调操作及对人出口的可靠性。目标设计；公共对象以 [协议](02-协议.md) 为准。

边界：内核不理解项目优先级、提示词或技术诊断。它校验状态和权属，不把固定词数、重试次数或工具调用次数当业务判断。

## 认领与事实版本

外部事件按来源命名空间与 event id 幂等认领。正式和 shadow 处置分开；一个正式事件只有一个处理者。消息、远端观察、操作回执和验收结果各自保留来源与时间。

人类指令先按 [世界模型的首期身份边界](04-世界模型.md#授权) 核验来源，再允许生成正式变更提案；非老板消息不能仅因语义像命令或已有项目授权而获得控制权。执行端反向请求按会话绑定归一为运行事实，与人类裁定分开，不能伪造老板授权。

判断基于明确的账本 revision、授权 revision 和会话 epoch。写提案时校验 expected_revision；版本落后则重新观察，不用旧案卷覆盖新事实。多对话可读同一责任状态，但不各自持有独立真相。

## 账本

只有内核打开运行账本写事务。其他模块提交经协议校验的提案；journal 追加记录，状态是由事实和合法迁移更新的投影。一个事务崩溃不产生半件事项或无关联尝试。

事项与职责、专业分工与资源锁、专业决定与审查问题、操作与回执、验收与交付分别记录。不能把阶段结束、会话消失、报告 ready 或发出消息当作完成事件。

父目标变更、旧拆解绑定失效及待执行动作版本门禁在同一事务中生效，规则归 [目标拆解协议](02-协议.md#目标拆解与整体验收)。失效后的在途动作继续保留事实并经撤销、对账处理，不能让模型稍后逐条通知子单成为唯一防线。专业合同、分工和关键决定变更同样校验依赖版本；关闭必需审查问题、替代验收结论和放行交付须符合协议的独立性及证据要求。内核校验结构与绑定，不裁定技术分歧。

```text
Ledger.transact(expectedRevision, proposals[]) → committed revision / conflict
Ledger.append(subjectRef, event) → eventRef
Ledger.transition(subjectRef, state, evidenceRefs[]) → revision
```

协议新增对象需要显式迁移；不维持「内核永不改变」的绝对承诺，但策略和适配器扩展不应侵入事务机制。

## 时钟与事件唤醒

事件优先触发协调回合，持久化 next_review_at 作为兜底。active 职责、非终态事项、等待依赖、未决执行端请求及未知操作都有复查计划。进程恢复补查过期检查点，而不补发所有历史轮询。

轻量预检可合并重复信号、限制空轮询；它不能永久挡住需要语义判断的复查。没有新日志但已到最晚复查时间，仍必须核实现场。ops=0 只作诊断读数，不能直接判定空跑或自动缩减观察覆盖。

停止、权限撤销、人工接管走高优先即时控制通道。资源隔离成立时，不同项目可并行协调；同一责任对象的写提案通过版本冲突串行化。

## 协调操作

宿主先持久化 Action，再检查授权、控制 epoch、资源锁和目标版本，最后由执行器适配器执行。所有可改变 Agent 或宿主状态的操作均走此路径。

- 同一幂等键重复提交只返回既有状态，不重复派发或发指令。
- 请求超时进入 unknown；对账读取远端事实，不假定失败后直接重放。
- 操作成功的权威是适配器回执与可观察状态，模型仅能提出操作。
- 接收输入与消费输入分别记账；未消费消息不能被结案漏掉。
- 反向请求应答与普通输入分别执行；响应意图持久化后再次核验原生请求有效性，解除事件仅更新请求事实，不直接完成事项。
- 会话控制租约与对人发送租约各自持有 epoch；持有发送权不等于拥有所有远端会话。

## 紧急控制持久化

停止、撤销和接管是减少权限的控制意图，不受「禁止新业务副作用」阻挡。控制面在账本之外保留只追加的本地紧急控制日志，写入成功后发送带 epoch 的撤销/取消；目标端也持久记录控制变更，恢复时先合并这些意图再调度业务。该日志只允许减少控制权，不能创建任务、授权或新写操作，不是第二个业务真源。

账本故障但紧急日志可写时仍可停止；本地所有持久化均失败时尝试现有连接上的幂等取消，并显示停止未持久确认。目标端租约到期仍应停止新增写入；在未读到远端停止证据前不能回复已停，不能释放占用锁。恢复时核对远端 epoch 与控制记录，禁止仅凭旧账本恢复被停工作。

全持久化不可用时不建立第二条 IM 推送通道：若本机只读状态接口或现有 GUI 控制请求仍可用，通过同步响应显示「停止未确认、持久化不可用」；它是操作状态读取，不冒充可重试的已送达消息。若所有查询/通信路径均失效，则无法保证向人反馈，记录为可用性故障并由独立健康监控发现；恢复后对账并补报，绝不能谎称已通知。

## 统一对人出口

受理、回答、交付、提问和简报都经 outbox。内部 Agent 协调走 Action，不伪装成人类聊天，也不能借通道绕过授权。

出口按实际受众核验披露、代理身份、授权承诺、通道长度与幂等。消息策略由时机模块提供，不在数据库中把所有正文限制为 100 词。一个入站一个语义答复；后续生命周期消息使用独立键，防止受理占用唯一 reply 后交付发不出去。

发送前再次检查租约 epoch、受众变化及消息依据是否已过期。排队中的旧完成消息在需求追加或验收失效后作废，不发送过期成果。

## 共存、shadow 与迁移

保留 responder/shadow/superagent 的可回退接入机制。shadow 只观察并记录拟处置；不得创建真实执行会话、发送提示词、取消已有会话、发布产物或写对人 outbox。测试 shadow 时要检查所有 Action 副作用，而不只检查消息表。

旧事件 owner、通道去重和回复重试迁移要保持兼容。回退时停止新协调写入，保留账本与未决回执；不能通过删新表回滚已经发生的副作用。目标协议迁移前必须验证旧进程不会误读新状态。

通道仍归 `channels/feishu`；平台凭据归 feishu 服务域，运行通知归 notify。通道只做归一、受众读取和发送，不决定事项完成。现有平台配置命名空间不因本设计被复制。

## 依赖、扩展与失败处理

内核只依赖协议；组合根注入事件归属、唤醒、操作授权与执行端口、出口策略。内核不 import 模型判断或某个项目模块。

| 失败 | 处置 |
| --- | --- |
| 重复认领、过期版本 | 返回既有结果或冲突，不重复副作用 |
| 发送/控制租约失效 | 拒绝旧 epoch 操作，保留待处理事实 |
| 时钟停摆 | 由独立活性检查恢复调度；不依赖老板发现日报没来 |
| 操作回执丢失 | unknown，对账后确认；无法确认时保留资源占用 |
| 数据库不可写 | 停止新业务副作用，入站在可持久化通道排队；停止/撤销按紧急控制路径执行 |
| 通道不可用 | 持久出站与补发策略；恢复时检查消息是否仍有意义 |

验证内核需要事件重放、崩溃窗口、租约过期、旧版本提案、需求追加后的过期交付和 shadow 零副作用反例。业务成功由验收模块证明，不由事务成功推断。
