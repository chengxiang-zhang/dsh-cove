# 内核：认领、账本、时钟、出口

职责：保证四件事在任何时刻成立——每条入站消息恰好一个负责人、每件承诺不丢、时间会推动判断、对人说的话只有一个出口。它是账本唯一写入者。

边界：不认识飞书、不认识模型、不认识"秘书"这个词。它不判断"该不该做"，只保证"谁负责、记什么、何时看、怎么说"这四件事不被绕过。

一个会因为加功能而改的部件不属于内核。本文件列出的四个原语，加任何能力、行为、记忆结构都不需要改。

## 四原语

```
claim(event) ──► 一个 owner（responder | secretary），写 intake
   │
   ▼
ledger ──► 只追加的 journal + 状态机受约束的 commitment
   │
   ▼
clock ──► 到点的承诺 → 宿主信号预检 → 请求一次判断回合
   │
   ▼
outlet ──► 租约 + 幂等键 + 词数上限 + 一入站一回复
```

### claim：认领

契约：

```
ClaimPolicy.decide(event, snapshot) → { owner: 'responder'|'secretary', route: 'judge'|'fastpath'|'passthrough', disposition? }
claim.claim(event, policy) → ClaimResult
```

- 一个事务内完成：给 `inbox_event` 写 `owner`（未设置才能写，CAS）、插一行 `intake`、写处置（`judge` 留空，`fastpath` 写具体处置，`passthrough` 写 passthrough）、返回处置上下文。同一事件重复到达时第二次是空操作（P3）。
- `fastpath`：宿主直接执行处置（release / 按序号答 / 表情 / decline），不再进模型。
- `passthrough`：把消息作为输入追加到该线程活订阅的执行体 journal（`kind='passthrough'`），不新建承诺、不新建尝试、不起桌子回合。这是 R3 的机械形态。
- 认领失败（已被别人认领）不是错误，返回 `already_claimed`，调用方闭嘴。
- `owner` 与 `route` 的判定不是内核的：内核只调用注入的 `ClaimPolicy`。组合根把判断模块的快路径接进来。

不变量：任何 `inbox_event` 行在 60 秒内必须变成有主（否则告警）；任何 `intake` 行的 `owner` 与 `inbox_event.owner` 必须一致。

### ledger：账本

契约：

```
Ledger.open(tx => ...)                      唯一写事务入口
Ledger.append(commitmentId, journalEntry)   追加，返回 seq
Ledger.transition(commitmentId, to, patch)  校验状态机后改
Ledger.recordAttempt(...) / recordOutbox(...)
Ledger.propose(origin: 'host', spec)        宿主发起 goal/remind/watch（origin_kind='host'）
```

`Ledger.propose` 只给宿主用：常设安排（每天 18:30 发简报）、到期提醒、目标都需要一件承诺，但它们没有入站事件可挂。约束：只有 `kind ∈ {goal, remind, watch}` 能由宿主发起，`origin_ref` 是宿主生成的唯一键；模型不能调它。

- 所有模块通过它写账本；没有第二个写入口（P1）。模块崩在事务里，账本不变。
- 状态机与表级约束由协议定义（见 [协议](02-协议.md) 的 commitment 状态机）；内核负责在写入前校验，违规返回 `ILLEGAL_TRANSITION`。
- journal 只追加；`request_id` 唯一，表达"这条输入只被执行体吃一次"。
- 承诺结案时宿主回填 `actual_min/attempts/executor_switched`，这是校准的唯一原料。

不变量：

- I1 不遗忘：`proposed/open/at_risk` 必须有 `next_look_at`；非 goal 类 ≤ 24 小时，goal ≤ 7 天。
- I2 一问一处置一答：每条被认领的事件恰好一个 disposition；每条入站至多一条 reply 档出站。
- I3 无主算力：`running` 的尝试必属未结案承诺且有预算；不在账本里的会话不是我们的。

### clock：时钟

契约：

```
Clock.tick(now) → { requested: TurnRequest[], deferred: CommitmentId[] }
TickSignal.has(commitmentId, now) → null | Signal   // 纯宿主计算，不调模型
```

- 每 60 秒一轮：取到点的承诺，先调 `TickSignal` 做无模型预检。
- 即时路径：老板说停、预算到线、派发失败终止句都不等时钟——release 意图与取消直接执行并写回执。时钟只管周期性的"看一眼"。60 秒内真停靠这条，不靠 tick。
- 无信号：机械后推 `next_look_at = now + max(5 分钟, 剩余预计/2)`，不请求回合。这是防空跑的第一道。
- 有信号：写一行 `deliberation(state=requested)`；组合根把它接到桌子的 `runTurn`。**内核不等桌子返回**，桌子崩了下一轮还能再来。
- 每个回合结束回写 `ops/tool_errors/tokens/end_reason`；`ops=0` 的回合占比就是秘书空跑率（G9 读数）。

不变量：`deliberation` 的 `request_id` 唯一；同一承诺同一时刻至多一个未结束回合（`turn_open`）。

### outlet：出口

契约：

```
Outlet.submit(proposal: SpeechProposal, policy: OutletPolicy) → OutboxId
Outlet.flush(now) → SendResult[]
SenderPort.send(chatId, text, idemKey, replyTo) → { messageId }
```

- 所有对人可见的东西（回复、表情、简报、告警）都走这里；没有任何模块能自己发消息。展示模块只提供模板，不提供发送。
- 提交时定档：`tier` 由 `OutletPolicy` 按注意力规则算，模型不能指定（R5 的机械形态）。
- 提交时校验：words ≤ 100、moment 与当前情境匹配、未授权承诺词拒发（R15）、不可说记忆命中拒发（R7 的"说"边界）。
- 发送前拿租约（单行 `lease`，带 epoch）；同库多进程只有持有者能发。跨机只能发现不能防止（见 [恢复与降级](11-恢复与降级.md) 的第二声音探测）。
- 失败重试沿用现成退避（30 秒起、24 小时放弃，F19）；放弃后在下一条出站末尾附一句"有一条消息没发出去"。

不变量：I4 一个声音：所有出站带当前租约 epoch；过期 epoch 的提交直接丢弃。

## 共存与接管：不动现在这条管道

现在的 `responder` 是一条在跑的应答管道；秘书是同一批事件上的第二个 owner。切换必须是加法，不是替换。

- 迁移只加不减：`inbox_events` 加可空的 `owner` 列，新建 `sa_*` 表；`responder` 的状态机与表一律不动。
- 开关有三档，逐消息生效而不是全局布尔：`responder`（现状）｜`shadow`（秘书照常判断、记账、算出站，但 `outbox.deliver=0`，一个字不发）｜`superagent`（秘书接管）。判定落在 `claim` 的 CAS 上：一条事件只有一个 owner，切换窗口里两边读到旧值也只会有一个人赢。
- `shadow` 期的判据：每条入站恰好一个 owner；秘书的处置与 responder 的回复在同一条消息上人工抽检一致；线上回复零重复；一条线程至多一件承诺。三条都成立才允许逐消息切到 `superagent`。
- 回退：把开关切回 `responder`，不迁移数据、不删账本；账本留着，下次切回时按 `event_id` 幂等继续。
- 旧状态机的去向：`reply_jobs` 与 `responder` 里"要不要回、回什么、什么时候主动说"被评为判断与出口后，`responder.ts`（1696 行）与 `reply-machine.ts` 的判断部分退役，`reply_jobs` 只保留出站重试。退役条件不是"新代码写完"，而是 lark-inbox 的 13 个 spec 里与 responder 相关的用例逐条迁到新模块并有等价读数——一条没迁完，旧代码就不删。
- 生效方式：新服务域进 bundle 后要用户重启才生效（F23）。重启前 `responder` 一直按旧逻辑跑，影子判断不发送。

## 依赖反转：内核怎么不认识上层

内核只定义四个接口，由组合根注入实现：

| 接口 | 谁实现 | 内核拿它做什么 |
| --- | --- | --- |
| `ClaimPolicy` | 判断（快路径规则） | 决定事件归谁、是否直接处置 |
| `TickSignal` | 时机与措辞（议程信号） | 判断到点的承诺有没有新信息 |
| `OutletPolicy` | 时机与措辞（注意力与模板） | 定档、选模板、做发送前校验 |
| `SenderPort` | 宿主（飞书管道） | 真正发出去 |

因此依赖图里内核在最底层，没有任何箭头从内核指向上层。加一个议程来源、加一条快路径、换一个渠道，都不需要动内核。

## 失败模式

| 失败 | 检测 | 处置 |
| --- | --- | --- |
| 认领双写 | `inbox_event.owner` 已有值 | 第二次写入失败即空操作；不重试 |
| 时钟停摆 | 最后一轮 tick 距今 > 3 分钟 | 简报兼心跳：承诺没结案而当天没简报，老板知道它死了 |
| 租约分裂 | 两个进程都持 epoch | 发送前校验；旧 epoch 丢弃并记审计；跨机靠第二声音探测 |
| 出口堆积 | `outbox.state='queued'` 超过 5 分钟 | 记 `failed`，下一条出站附一句；不无限重试 |
| 状态机违规 | `ILLEGAL_TRANSITION` | 拒绝写入并记一条 `tool_errors`；不回滚其他已提交操作 |

## 扩展点

没有。内核是关闭的：它只接受四个接口的实现注入。加能力、加行为、加记忆结构都不改内核；如果某个需求必须改内核，说明它动的是不变量，要先改需求基线。

## 读数

```sql
-- I1
SELECT count(*) FROM commitment WHERE state IN ('proposed','open','at_risk') AND kind<>'goal'
  AND next_look_at > strftime('%s','now')*1000 + 86400000;                    -- 0
-- I2
SELECT count(*) FROM inbox_event e LEFT JOIN intake i USING(event_id)
  WHERE e.owner='secretary' AND (i.state IS NULL OR i.state<>'disposed')
  AND e.received_at < strftime('%s','now')*1000 - 600000;                     -- 0
-- I3
SELECT count(*) FROM attempt a JOIN commitment c USING(commitment_id)
  WHERE a.state='running' AND c.state NOT IN ('open','at_risk');              -- 0
-- I4
SELECT count(DISTINCT lease_epoch) FROM outbox WHERE state='queued';         -- 1
-- 秘书空跑率
SELECT round(avg(ops=0), 2) FROM deliberation
  WHERE started_at > strftime('%s','now')*1000 - 86400000;                    -- < 0.3
```

## 为什么不是另一种

- 为什么不做成"一个更聪明的会话"：会话会被压缩、换代、重启；真相放会话里，重启就丢。账本是可重建的，会话是可丢弃的。
- 为什么内核管出口而不是各模块自己发：Hermes 事故（一条消息收到 8 个回复，F34）证明多出口必然抢答；出口唯一还要跨进程租约（F19）。
- 为什么时钟是内核原语而不是定时任务：定时任务只会在进程活着时跑；重启对账要能补上错过的到点（见恢复与降级）。
