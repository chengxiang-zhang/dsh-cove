# Architecture

dsh-cove is an extension suite for the DeepSeek Harness (DSH) Web GUI. It is packaged as one runtime entity plugin so that a profile mounts a single row and every capability shares one lifecycle. This document explains the repository layout, the runtime model, the extension seams and the release model; deep technical contracts stay with their owning documents and are linked at the end.

![dsh-cove architecture](architecture.svg)

## Repository map

| Path | Responsibility |
| --- | --- |
| `packages/dsh-web-all/` | The only runtime entity: host service domains, browser position modules and bundled presets |
| `packages/dsh-community-plugins/` | Community plugin index data source; no runtime row |
| `shared/` | Cross-package runtime and tooling helpers, including the single client build preset |
| `scripts/` | Repository maintenance, audit, release and generation scripts |
| `config/` | Committed templates for machine values; real values stay untracked |
| `docs/` | Long-lived documentation |
| `tools/` | Self-hosting, packaging and client tooling around a DSH deployment |

## Runtime model

A DSH profile resolves a bundle stack. dsh-cove does not replace that stack; it adds one entity row and a few preset patches:

```text
profile (web | desktop)
  -> @deepseek-ai/dsh-base          core host services
  -> @deepseek-ai/dsh-web-app       web runtime, browser shell
  -> @dsh-cove/dsh-web-all          one entity row: web-all
       -> host services             register(ctx) per service domain
       -> browser position modules  sidebar / conversation / settings
```

`packages/dsh-web-all/cordis.patch.yml` declares the single `web-all` row. Preset patches may add Agent presets or a model route, but they never add a second functional entity. A capability is a service domain inside the same plugin, not an independent package, so there is no second Cordis lifecycle to mount, version or dispose.

## Extension seams

Browser code is organized by DSH injection position. Each position has exactly one owning module, which performs every slot or DOM registration for that position; capability files are assembled by that module.

| Position module | Owns |
| --- | --- |
| `src/client/sidebar/` | Sidebar panel rows, the sidebar `main` body and right-pane tabs |
| `src/client/settings/` | Built-in plugin settings tabs, currently Feishu intake and run-finished notifications |
| `src/client/conversation/` | Composer dock, session header actions and the branch selector |
| `src/core/` | Pure protocols and algorithms shared by host and browser halves |

Host capabilities are service domains under `src/host/services/<domain>/`, each exporting `register(ctx)`. The assembler in `src/index.ts` calls every domain and keeps the plugin's single lifecycle. Cross-half wire types live in `src/core/<domain>/`.

## Access model

Every privileged host route family goes through one shared fence, `accessTrustOf(ctx)`: the request socket must be loopback, the Host must be loopback or an authority the deployment declared with `--trusted-host`, and the request must carry an authenticated DSH browser session plus same-origin markers. Read-only routes are privileged too. A remote entry gets its Host ownership from a per-request boot script, and the plugin injects polyfills for browser APIs that a plain-HTTP entry lacks. The invariants, the accepted topologies and the audit commands are defined in the [remote-access contract](remote-access.md); the plugin-side security consequences are in the [dsh-web-all security model](../packages/dsh-web-all/README.md#security-model).

## Generated artifacts

- Package copies of `shared/` modules are generated by `scripts/sync-shared.mjs` and must not be hand-edited.
- `config/templates/*.tmpl` render into build outputs through `scripts/config-render.mjs`; only the template and the example file are committed.
- Documentation pairing records are generated by `scripts/verify-docs.mjs --write`.

## Release model

A `vX.Y.Z` tag is the only version source. Tags are cut from `main` after `dev` is integrated and tested; every publishing workflow first proves the tag commit is on `main`, then the tag publishes the two npm packages and attaches the desktop and Android installers to the GitHub Release (iOS builds only run when Apple signing secrets are configured). Release notes are generated from Git history into GitHub Releases. The full gate list and registry rules are in [publish-prep.md](publish-prep.md).
