# 卡片 · 派工 · 回执 模板

## 1. 任务板卡片（一卡一任务）

```
subject: T01 · <主题>（PG-x）        # blocked 时改成 [BLOCKED: <原因>] T01 · …
description:
  目标：<一句话可判定的目标>
  交付物：<文件/行为/门>
  写域（互斥）：<路径 1>、<路径 2>…
  验收门（账本）：GAP-a、GAP-b —— <命令/断言> ⇒ <期望读数>；负控 <注入> ⇒ 必红
  依赖：<卡 id 或"无">
  独立性：不碰 <共享文件/他人写域/生成物>
write_scopes: [ … ]                   # 与"写域"逐条一致
blocked_by: [ <卡 id> ]
```

**包类卡**（一包一卡）可简化为：

```
subject: PKG-<slug>
description: 包 `docs/specs/<id>/`（VERSION 状态 ready）。真源：`INDEX.md` §3 该行（条目/写域/依赖）
  + 本包 `tests.md`（验收）+ `EXECUTION-LOOP.md` §2（单轮协议）。环内只做 G0/G1；
  关条由 Lead 在收口点批量执行；跨仓与开窗归 Track-B。首轮必须先做 S3 必要性自证（先红再改）。
write_scopes: [ … ]
```

**目标类卡**（带现状与路径，后期最有效）：

```
subject: T-<name> <条目>
description:
  验收门：<条目自己的门>。
  现状（Lead 已核实，别重复查）：<命令 + 读数>。
  你要做：①… ②… ③…（每步给入口命令或 file:line）
  写域：… 禁改账本/INDEX/宪章/批次台账，禁 commit，禁 push。
```

## 2. 派工消息（send_message）

```
【派工 · <卡 id> <标题>】

一、现状（我已核实，别重复查）
- <读数>：`<命令>` ⇒ `<结果>`
- 结论：<哪些已通、缺口在哪>

二、目标
<一句话；写明"可关/还差什么"的判据>

三、要做什么（按序）
1. <步骤>：`<命令或 file:line>`
2. <步骤>：…
3. <验证>：`<门命令>` ⇒ 期望 `<读数>`；负控：<注入> ⇒ 必红

四、写域与禁止
- 只写：<路径>
- 禁：改账本/INDEX/宪章/批次台账；commit；push；改他人文件；<其它红线>

五、回执（必须五段）
① 写域清单（逐文件 + "未改账本/他人文件"）
② 每条目处置（id → 处置 → 命令 + 读数）
③ 未证实项（Unverified: 缺什么）
④ 冲突/需裁决（needs-decision=）
⑤ 判定：可关 / 还差什么

六、停手条件
- 超时 <N> 分钟；同一问题卡 2 轮；发现需裁决 ⇒ 停手回报，保留现场，不许硬猜。
```

## 3. worker 回执（模板）

```
<卡 id> 回执 — <worker 名> — <时间>

## 1. 写域清单
- docs/specs/…（新增/修改）
- 未改：账本 / INDEX / 宪章 / 批次台账 / 他人文件
- `git status --porcelain` 只含以上路径

## 2. 每条目处置
| 条目 | 处置 | 证据（命令 ⇒ 读数） |
|---|---|---|
| GAP-a | 关闭 | `pytest …` ⇒ 12 passed；`psql …` ⇒ 0 行 |

## 3. 未证实项
- Unverified: <缺环境/授权/数据>

## 4. 冲突 / 需裁决
- needs-decision=<问题>；我倾向 <A/B>，理由…

## 5. 判定
- 可关：<条目>（证据齐 + 负控红）
- 还差：<条目>（差 <具体一步>）
```

## 4. Lead 验收（回复 worker 的模板）

```
Lead 验收反馈（必修 / 通过）
1) <门> 我实跑：`<命令>` ⇒ <读数>；你报的 <读数> 一致/不一致（不一致以我为准）。
2) 越界：<文件> 不在写域内 ⇒ 回退该文件。
3) 缺项：<负控/未证实项/材料> 未给 ⇒ 补。
4) 通过部分：<卡 id> 我提交 <sha>（验证：<命令> ⇒ <读数>）。
5) 下一步：<唯一动作>。
```

**Lead 验收四原则**：自己跑门；不采信"绿"；越界即打回；只提交绿的。

## 5. 板卡卫生（每轮恢复态做）

- 派工即 `claim`（owner = worker）。
- 模块/批次收口即 `complete`。
- 长期 blocked 的卡：subject 加 `[BLOCKED: 原因]`，并在描述里写复活条件与 owner。
- 卡与实际脱节（卡 pending 但包已 done）⇒ 当场修，别留着当"假前提"。
