# 反模式清单（本方法来源会话真实翻车）

| # | 反模式 | 后果 | 正确动作 |
|---|---|---|---|
| 1 | 用脚本/`sed -i` 批量改账本 | 违反用户铁律，且改坏后难回滚 | 逐条 `read+edit`；必须批量时 commit 披露 + 全文档门 |
| 2 | 物理重排条目顺序 | 40 处 `path:line` 引用全红 | 只加 §0 总览与归属标注，不动正文顺序 |
| 3 | 计数口径多处不一致 | 用户当场质疑"进展是不是 0" | 三处一致 + 口径命令 |
| 4 | 条目无可执行验收门 | 关条靠嘴，无法判真 | 无门的条目先补门，补不出就判废 |
| 5 | 过度设计条目没杀就派工 | agent 花几天做"没人用"的能力 | 阶段 0 五类判据先杀 |
| 6 | 任务切太细 | 每轮都在等环境，墙钟全浪费 | G0~G3 粒度表；批次跨回合 |
| 7 | 把"包 code-ready"当完成 | 包 30/30 done，清单仍 70 条 open | 出口 = 条目归宿 + 证据 |
| 8 | 在方案文档里"私藏"新缺口 | 双账本、口径漂移 | 新缺口先写进唯一账本再派工 |
| 9 | 一次性把 100+ 条都做成 spec 包 | 设计件膨胀，施工反而更慢 | 先按方案组分批：先做一组验证节奏 |
| 10 | 只做正控不做负控 | "门绿"但缺陷仍可注入 | 每条 case ≥1 负控，负控必须红 |
| 11 | 先建 30 个包再裁决"值不值得做" | 沉没成本极高（真实：包建完才杀 32 条） | 先过价值门，再进施工包 |
| 12 | 关条/归档不扫下游锚点 | 全绿契约门被打红且长期不回绿 | 先 `grep -rl` 建锚点图，同批改锚点 |
| 13 | 复核前置引用空覆盖台账 | 用 1/18 的覆盖当门槛 | 先数覆盖 `x/y`，不足写 `missing=` |
| 14 | 权威数字无生成命令 | 4/6 错、1 小时更正 3 次 | 每个数字附命令 + 时间戳 |
| 15 | KILL 用"我觉得没用"或越权实验当证据 | 32 条"杀"里 17/17 仍写 blocked、4 条 P0/critical | KILL 五条件，缺一不算 |
