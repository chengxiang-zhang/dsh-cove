# 账本与合并设计方案模板

> 复制后按项目改；**所有「数字」都必须有可复跑的口径命令**，否则删掉该行。

## 1. 唯一账本（`docs/product/<ledger>.md`）

```markdown
<!-- kind: ledger — 开放差距与关闭记录账本 -->

# <项目> 当前差距账（唯一未闭环事项清单）

> **口径**：只保留 `open / partial / accepted-risk / proposed（待裁决） / 待复核 / blocked(<类>)`。
> `blocked(<类>)` 是**归宿**不是进度标签：必须同时写「阻塞物 + 复现命令 + 复查日」三要素，缺一即按 `open` 计。
> **已闭环 / 已裁决 / 已证伪 / 已退役的事项一律从本账删除**，并进文末「已从本账删除（不再跟踪）」索引。
> **条目纪律**：新增条目用 `### GAP-<系列><编号> · 标题`，必须给**可证伪的验收门**（可执行命令或断言）
> 与**方案组归属**；只写散文、无可执行判据的不得入库。

## 0. 状态总览（按方案组收口）

> 计数口径命令：`grep -cE '^### GAP-' <本文件>`；严重 = 状态栏含 `P0|critical|high` 的条目数。
> 当前 **开放 N / 严重 M**（与下表两列合计、与下方严重清单 id 数三处一致）。

| 方案组 | 主题 | 开放条目 | 严重 | 系统性根因（一句话） |
|---|---|---|---|---|
| **PG-1** | … | 3 | 2 | … |

**严重条目清单（M 条）**：`GAP-xxx`、`GAP-yyy`

**方案组 → 条目归属**

| 方案组 | 条目 |
|---|---|
| PG-1 | `GAP-xxx` `GAP-yyy` |

## 已接受风险登记（**不计「未处理」**；每条必须有接受人 + 复核日 + 重开条件）

| 条目 | 风险 | 接受人 | 复核日 | 重开条件 |
|---|---|---|---|---|

## 1. <按来源批次> 条目正文（物理顺序不搬迁）

### GAP-xxx · 标题

- **状态**：open（P0；归属 PG-1）
- **事实**：一句话事实 + 证据路径/读数
- **验收门**：`<可粘贴命令>` ⇒ 期望读数
- **依据**：日志/演练/评审编号（可选）

## 已从本账删除（不再跟踪）

### 2026-10-28 第一批（关闭/裁决/归档）

| 条目 · 标题 | 依据 | 日期 |
|---|---|---|
| GAP-xxx · 标题 | `命令` ⇒ 读数；或「能力不存在」 | 2026-10-28 |
```

**写账本的三条硬规则**

1. **单写者**：只有 Lead 在收口时改账本（删条 + 索引 + §0 重算）。worker 只报告"我关掉了哪些 id"。
2. **改措辞不算账本动作**：「收缩阻塞说明 / 更正描述 / 补记录」都不产生净变化，不得计入进度。
3. **blocked 三要素**：阻塞物（谁/哪个仓/哪个窗口）+ 复现命令 + 复查日。写不出 = 仍是 open。

## 2. 合并设计方案（`docs/product/<plan>-<date>.md`）

```markdown
# <项目> 收口方案与任务分解（YYYY-MM-DD）

> **定位**：本文**不是第二本账本**。唯一清单是 `<ledger>`。本文只做两件事：
> ① 把 §2 的 N 个方案组写成**系统性解法**（一次改造覆盖一组条目，而不是逐条打补丁）；
> ② 把它们切成 §3 的 M 个**互相独立任务**（写域不相交、可单独验收、可并行派工）。
> 读法：§1 系统性结论 → §2 方案组解法 → §3 任务表 → §4 并行安全与调度纪律 → §5 裁决记录。

## 1. 归纳出的 K 条系统性结论

|---|---|---|---|

## 2. N 个方案组的系统性解法

| 方案组 | 一次改造覆盖什么 | 完成判据（账本门） | 需窗口 |
|---|---|---|---|

## 3. 任务分解（M 个，互相独立）

### 3.1 独立性判据（先立规矩，再派工）

1. **写域不相交**；共享目录下各自拥有具名文件；
2. **生成物单属主**：生成器 + 产物 + 对应门三元组独占，别人只读；
3. **可单独验收**：独立命令/断言/负控，不依赖他人产出；
4. **不写唯一账本**。

### 3.2 代码/文档类（可并行）

| 任务 | 方案组 | 交付物 | 写域（互斥） | 验收门 | 依赖 |
|---|---|---|---|---|---|

### 3.3 窗口类（串行）

| 任务 | 方案组 | 内容 | 前置 | 验收门 |
|---|---|---|---|---|

### 3.4 建议排期（按降风险/降成本，不按编号）

1. 第一档（无窗口、低风险、立刻降假绿）：
2. 第二档（契约与出口）：
3. 第三档（窗口，串行）：
4. 跨仓并行：

## 4. 并行安全与调度纪律

- 一任务一 lane / 一写域；lane 只用于隔离写入，**验收回主树并先记基线**；
- 生成物不得手改；改生成器，不改产物；
- 唯一账本单写者；
- 验收必须运行态证据（对象/SQL/指标/恢复），`health`/`smoke`/Pod Running 不算；
- 每个任务至少一条负控。

## 5. 裁决记录（YYYY-MM-DD 用户）与授权

| # | 问题 | 裁决 | 落实位置 |
|---|---|---|---|
| Q1 | … | **…（默认：…）** | … |

**授权边界**：明确「授权了什么」与「仍然不变的仓库红线」（不推上游 / 密钥不入库 / 重编译与冷重建不并发 / 不改他人资源）。
```

**方案文档防漂移三条**

- 不新增状态列：每条任务的完成判据都引用账本条目自己的门。
- 不新增条目：发现新缺口先写进唯一账本，再回来派工。
- 方案组是**归口**不是施工队：一个任务可覆盖多组，但一个条目只归一组。
