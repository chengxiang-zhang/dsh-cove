# 大清单 → 合并设计 → 独立任务

> **Entry tier: T3 only.** Score ≥7 or ≥10 open items / ≥3 modules. Below that, do NOT build a ledger or spec packs — use `change-spec` (T2) or `fix-loop` (T1).


把一个「几百行、多批评审堆出来、同一根因被登记多次」的待办清单，收敛成三件事：
**① 一本可判真的唯一账本 ② N 个方案组（一次改造覆盖一组） ③ M 个写域互斥、可单独验收的任务/施工包。**
这三件是 Agent Team 长跑的输入；没有它们就派工，等于把空跑分包给更多人。

**判据先行**：本 skill 的任何产物都不是"好看的文档"。每一行都要能回答——**谁执行、写哪些文件、哪条命令证明它对**。
回答不了的行不许进账本、不许进任务表、不许派工。


## 产出物（5 件，缺一不可）

| # | 产物 | 位置建议 | 谁读它 |
|---|---|---|---|
| 1 | **唯一账本**：开放条目 + §0 方案组总览 + 已删除索引 + 已接受风险登记 | `docs/product/gap-register.md` 或等价 | Lead 每轮；worker 取条目 |
| 2 | **合并设计方案**：系统性根因 F1… / 方案组解法 / 独立任务表 / 裁决记录 | `docs/product/<plan>-<date>.md` | Lead 派工；用户拍板 |
| 3 | **施工包总纲**（可选但强烈建议）：包登记表 + 接口冻结表 + 联调矩阵 + 效率手册 | `docs/specs/<id>/{INDEX,INTERFACES,INTEGRATION,EFFICIENCY}.md` | worker 只读本包 + 接口表 |
| 4 | **N 个模块包**：`VERSION/contract/tests/plan/run` 五件 | `docs/specs/<id>/` 一包一模块 | 一个包 = 一个可派单元 |
| 5 | **派工准备**：任务板卡片（含写域）+ 派工协议 | 共享任务板 + 本 skill §6 | Agent Team |

## 阶段 0 · 清单体检（先杀再做，节省的是指数级成本）

**先问一句：清单里的问题，现在还是真的吗？** 多批评审堆出来的清单里，常见 30%~50% 已经自愈、已退役、或本来就不该存在。
先做 P0 复核，别急着给每个条目设计施工。

### 0.1 P0 复核：四判定（每条给命令 + 读数）

| 判定 | 含义 | 动作 |
|---|---|---|
| `仍存在` | 当场取证确认缺陷仍在 | 正常施工 |
| `已解决` | 已有运行态/门证据证明不存在 | **直接关条**（不写实现） |
| `描述过期` | 缺陷在，但描述/路径/口径过期 | 先修描述再施工 |
| `无法判定` | 缺环境/授权/数据 | 写 `missing=`，标 blocked 候选，**不许凭猜开工** |

- **复核必须由「要干活的人」当场自己跑**，不能引用上一轮台账的结论：台账只是**线索库，不是门槛**。
- 台账里"已解决"但无命令的行，一律按 `无法判定` 处理。
- 反例（真实翻车）：把旧台账里的判定当结论引用，结果 10 条"待修"里有 7 条早已修好，白干两天。

### 0.2 杀假问题（一次杀完，不许一条条停）

五类判据，命中即 `KILL`（标题降级保留原文可审计，移出开放计数，**记录重开条件**）：

1. **能力不存在**：要求的能力在当前产品范围里根本没有（`grep`/`psql` 0 命中）。
2. **对象已退役**：条目描述的表/服务/产品线已下线或已宣布退役。
3. **已自愈**：运行态读数直接证明问题不存在。
4. **无消费方**：功能在，但没有任何调用方/使用者（"建了没人用"）。
5. **过度验证/过度设计**：把"应该做到"写成门，但收益为零、成本按人周算（典型：给测试夹具做合规评级）。

**纪律**：一次批量杀完并**附每条的只读证据**；不要"每轮杀 2 条"——那是把用户的时间当燃料。
被杀的条目必须写**重开条件**（什么新证据出现才重新开），否则下个月会被当新问题再提一遍。

**KILL 五条件（全预设唯一版本，缺一不算）**：

1. **能力/对象确实不存在**：只读命令 0 命中（不是"我觉得没用""成本高""没有第二租户"）。
2. **证据当轮可复跑**：命令 + 输出片段；不能拿另一批的读数或队友回执。
3. **不由越权/无授权实验得出**（真实反例：某条目的 kill 依据正是 Lead 自认越权的 5 轮集群实验，其中一次造成页面 000）。
4. **判据不放宽**：杀之前若先改了判据（把"34 处引用"降成"grep>0"），按事故记。
5. **merge 目标存活且 P0 未被静默降级**（真实反例：`IR11` 合并进 `RV12`，而 `RV12` 同提交被归档）。

**状态名**：KILL 行写 `closed-by-decision:<原因码>`，不得与 `blocked(...)` 并存；P0 降级必须引用用户裁决。
**滥杀偏差（A26）**：把"成本高/无第二租户/暂时没人用"当"能力不存在"是判断，不是否证——这类只能记 `accepted-risk`（带复核日）。

**价值门（先于写 spec 包）**：在把条目做成 30 个施工包之前，先做一次"值不值得做"的裁决。
真实教训：30 个包全部建完、写完 164 个文件之后，才批量杀掉 32 条——沉没成本极高。
价值门判据：有没有真实消费方/交付期限/合规义务？没有就 KILL 或 accepted-risk，不要进入施工包阶段。

### 0.3 归档已闭环

- **从开放账删除**，并把「条目 · 一句依据 · 日期」写进文末日期化索引（供追溯与防重复提出）。
- **不许**保留"已完成"状态行混在开放账里：开放账只有 `open / partial / accepted-risk / blocked(<类>) / 待复核 / proposed`。
- **不许**用脚本批量改文档（铁律）。真要批量，先 commit 说明里显式披露，并当场把全部文档门跑绿——否则宁可逐条 `read+edit`。

**阶段 0 出口**：`§0 总览` 数字与「`###` 标题重算」逐条相等；已杀/已关/已接受各有具名清单与证据。
**任何数字必须附生成命令**（真实翻车：切片映射 4/6 错、1 小时内更正 3 次，全靠 worker 反算）。

**下游锚点图（归档/关条前先建）**：`grep -rl "GAP-<id>" docs/ scripts/ deploy/`，记录"谁引用了它"。
真实翻车：一次 11 条关条把全绿契约门打成 `4 failed / 30 passed / 9 skipped`，两天未回绿——因为契约文档把被删条目当锚点。

## 阶段 1 · 归并去重（同一根因只留一个承载条目）

- 同一根因被多次登记 ⇒ 合并为**唯一承载条目**，其它进删除索引（id 保持可解析，防引用断裂）。
- **物理顺序刻意不搬迁**：条目正文留在原位，只用 §0 总览表 + 各节标题表达归属。
  重排会让所有 `path:line` 引用与外部锚点一起漂移，收益为零。（真实翻车：重组后 40 处引用全红。）
- 计数口径必须**三处一致**（§0 表两列合计 = 严重清单 id 数 = `grep` 重算数），并写出口径命令。

**§0 总览表（模板）**

| 方案组 | 主题 | 开放条目 | 严重 | 系统性根因（一句话，不是逐条补丁） |
|---|---|---|---|---|
| `PG-1` | 发布身份与供应链单一真源 | 3 | 2 | 同一事实在多处声明，且溯源门默认可 SKIP ⇒ 身份不可追溯 |

## 阶段 2 · 系统性归因（方案组 = 一次改造覆盖一组）

不要按"文件/模块"分组，按**根因**分组：一条根因对应一次结构性改造，完成后同组条目的验收门应当**成批**转绿。
如果只有一条转绿，说明改的是补丁而不是根因。

**F 类根因清单（套用后再按项目改）**

| 类 | 根因 | 结构性解法 |
|---|---|---|
| F1 | 同一事实多处声明（锁/清单/配置/台账/命名） | 单一真源 + 派生 + **方向性断言**（只禁放宽，允许收窄） |
| F2 | 决策点后置（授权/校验发生在副作用之后） | 把判定前移到唯一入口，未授权在副作用前拒收 |
| F3 | 声明 ⇄ 运行态脱钩（离线门绿、线上不存在） | 三方对账门：声明 → 投影 → **运行态读数** |
| F4 | 生命周期/保留没有单一声明 | 一份策略真源（对象 → 保留 → 动作 → 执行体 → 门） |
| F5 | 证据面缺失（失败只进 stdout、告警无人应答） | 每个失败面有指标 + 规则 + 到人闭环 |
| F6 | 热路径无预算 / 事实源同时承载状态与处理 | 预算声明化 + 状态与处理解耦 + 输入来自运行态采样 |

**每组必须写**：覆盖条目（引用条目自己的验收门，不另立门）、一次改造覆盖什么、**需不需要环境窗口**。
需要窗口的组单独成"串行任务"，与代码类任务不互斥（先改代码，后进窗口）。

**裁决记录**：所有需要用户拍板的点集中成 Q1…Qn，**每条给默认值**（"不回则按默认执行"），一次问完。
用户答完就写进"裁决记录（已生效）"，后续不再重复问。

## 阶段 3 · 独立任务切分（可并行派工的四判据）

一个任务**可独立派工**，当且仅当四条同时成立：

1. **写域不相交**：文件/目录前缀与在跑任务无交集；共享目录下各自拥有**具名文件**。
2. **生成物单属主**：涉及生成物时，任务独占「生成器 + 产物 + 对应门」三元组，别人只读。**产物不得手改**。
3. **可单独验收**：有独立命令/断言/负控，不依赖别人产出才能判绿。
4. **不写唯一账本**：任何任务都不得改账本；任务只**报告**自己关掉哪些 id（Lead 单写收口）。

**任务表（模板）**

| 任务 | 方案组 | 交付物（一句话） | 写域（互斥） | 验收门（取自账本） | 依赖 |
|---|---|---|---|---|---|
| `T01` | PG-1 | 制品身份三处声明收敛为单一真源 | `deploy/governance/a.json`、`scripts/tests/t1.py` | `IR03` `IR31`（三侧逐字相等 + 两门绿） | 无 |

**排期按"降风险/降成本"而不是编号**：先做"门与证据"类（改完同族条目成批转绿），再做契约/出口类，最后窗口类。

**粒度纪律（防止把任务切碎成空跑）**

| 档 | 典型改动 | 验证 | 动环境？ |
|---|---|---|---|
| G0 单点 | 一个函数/一条规则/一处措辞 | 该单元测试先红后绿 + 1 条负控 | 不动 |
| G1 包内切片 | 多文件、契约形状、生成物一致性 | 包内用例 + 契约门；生成物用 diff | 不动 |
| G2 生效批 | 需在集群/环境生效的配置/策略/镜像 | 批内每项先有 G0/G1 证据；批级一次 apply + 回读 | **一次、攒批** |
| G3 跨模块/系统 | 链路、恢复、安装、守恒 | 联调矩阵 + 基线复算 | 单窗口串行 |

**禁止**：为一行配置重启服务；为单个改动开窗；一个任务切到"每次只改一个字段然后等环境"。

## 阶段 4 · 施工包（让 worker 只读一个包就能开工）

包的目的不是文档齐，而是**并行施工不撞车、拼装不接口错配**。

### 4.1 一包一模块，五件必填

```
docs/specs/<id>/
  VERSION.md    # 状态机 draft|ready|in-progress|verifying|blocked|done|archived|cancelled + Delivery Target + 依据
  contract.md   # 一句话目标 + 入口事实映射 + Requirements（含越权反例）+ 复核前置（阶段 0 判定）
  tests.md      # T-case 索引：≥3 条，每条带命令 + 期望 + 负控（注入缺陷必须变红）
  plan.md       # 切片表：切片 id / 入口 / 完成定义 / 触及路径 / 依赖
  run.md        # 执行态：只追加结构化行（≤10 行/轮），禁叙事
```

**包自足判据**：一个 fresh agent 只读「本包 + 接口冻结表」就能开工，不需要读别人的包、不需要猜接口、不需要改账本。

**复核前置的覆盖检查（新增）**：若"复核前置"引用某份兄弟台账（如 reverify ledger），先数它的覆盖：
`x/y 条有判定`。真实翻车：台账只覆盖 18 条中的 1 条，却被要求当门槛；也出现过点名不存在的 `run.md` 路径。
覆盖不足时写 `missing=`，不许用"空目录/空表"当已读。

**每包必带**：① 本轮角色基线（作者/施工者/复核者，角色变了要声明作废旧写域）；
② 回执格式（交付型五段 / 快答型三段）；③ 停手条件。

### 4.2 总纲三件

- `INDEX.md`：包登记表（包 → 账本条目 → 写域 → 依赖）+ **派工协议**（worker 第 0 步自己复核"问题是否真的还存在"；台账只是线索）。
- `INTERFACES.md`：跨包唯一合法耦合面。每条 = 载体 + 可判定契约要点 + 版本纪律（`free` / `dual-write` / `frozen`）。**没登记就是越界依赖**。
- `INTEGRATION.md`：联调层级（L0 单元 → L1 包 → L2 模块 → L3 系统）+ 每层判据 + **每条 case 必须有负控**；下一层未过不进上一层。

### 4.3 出口判据写在包外

**包的 `code-ready` 不是完成。** 出口唯一判据是：**账本条目被它自己的验收门证据满足**（或具名外部 blocked）。
把"30 个包全部 done"当出口，会出现"包全绿、清单一条没关"的假完成——这是本方法来源会话里最严重的一次翻车。

## 阶段 5 · 派工准备（把设计变成团队可执行的东西）

1. **任务板卡片**：一卡一任务，字段见 `agent-team-project-loop` 的 `references/card-dispatch-report.md`；写域随卡登记。
2. **写域登记**：所有卡的写域并集不得冲突；共享文件（账本/INDEX/宪章/板卡/commit）**只 Lead 写**。
3. **派工协议**写进 `INDEX.md`：worker 开工第一件事是**自己复核必要性**（四判定），不是直接施工。
4. **出口报告骨架**提前建好（`HANDOFF.md` 模板）——它逼你现在就想清"什么算完成"。

然后加载 **`agent-team-project-loop`**，按它的宪章开环。

## 窗口预算与断点续跑（2026-10-31，A-06）

真实 GUI 单轮可能只有几分钟，T3 大清单不可能一轮吃完。硬规则：

1. **每 8 次工具调用或每个批次结束**，更新账本里的 `BATCH-STATE.md`（当前批次、已关 gap、下一批、命令读数）；
2. 单轮**先交付一个可验收批次**（含四数与回读），**不要**在同一轮里串 30 条；
3. 轮末若还有 open gap：在回复最后一行写 `RESUME: <下一批编号> <命令>`，让下一轮可精确续跑；
4. 新轮开头**先读 `BATCH-STATE.md`**（或 run.md），从 `RESUME` 处继续，**禁止从零重扫**；
5. 续跑仍按原批次顺序，不跳批、不并发改写同一写域。
