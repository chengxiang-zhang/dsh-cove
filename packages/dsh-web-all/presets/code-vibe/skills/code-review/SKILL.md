# Code Review（评审方法论）

> 提炼自 DeepSeek Harness 的 dsh-code-review（MIT），去除仓库绑定，适配许愿项目（wish-programming 切片实现 + 本地 skill 体系）。
> **Guidance, not a complete checklist.** 先确认评审对象的真实改动范围（相对验证过的基线，而非随意 ref——见 `agent-operation` 最小验证集），再读 diff 与足够上下文理解设计。

## 评审依据（Sources of truth）

- `wish-programming`：五阶段流程、原话优先、报告协议——切片是否遵守已锁定规范单？
- `frontend-design`：设计类愿望的字段门/白名单——实现是否发明组件/布局/样式？
- `quality-review`：验收证据标准——测试/截图是否证伪过？
- `dsh-prose-standard` + `dsh-trim-cot-leakage`：注释/文档/文案质量与思维链泄漏。
- `dsh-ci-test-reliability`：切片测试的确定性与反 flake。
- 决策记录（docs/wish/<id>/ 的 design-spec 备选方案节）：与已记录决策冲突 = 设计讨论而非自动否决。

## Blocking requirements（机器查不出的才列在这里）

1. **契约与规范对照**：实现与 design-spec/需求清单（N/O 编号）逐条一致；与原话冲突处有登记或回用户。
2. **证据存在且匹配声明**：作者声明的测试/截图真存在、真跑过（对照 `agent-operation` 报告纪律：只报实跑命令）；CI/门禁已覆盖的不重复提。
3. **白名单合规**：新组件/布局/样式出现 → blocker（除非用户在拍板点批准过；`check_whitelist.py` 是机械下限，评审补语义判断）。
4. **用户可见行为有证据**：文案改了但确认包没同步 → blocker；模型/用户可见字符串必须有对应证据（多视口截图或快照）。
5. **生命周期与副作用**：资源/订阅/监听有清理（dispose）；失败路径不静默吞错（空 catch 具名）。
6. **文档随代码**：README/注释/模板与实现同 PR 更新；推理转录与 review 历史不写进注释。
7. **不越范围**：评审目标之外顺手改动 → 要求拆出或说明必要性（投机泛化：为不存在的未来加的抽象/配置项）。

## Manual checks（按需逐项）

- **意图与接口**：切片 brief 与实现一致（含错误、取消、所有权、清理）；public 新方法只有一个内部调用者 = 疑似过度扩展。
- **状态与并发**：异步设置/回调/拆除顺序；取消中的 await；发布前竞态；回调包含；重入前所有权。
- **用户视角**：目标用户 + 做完后用户能看到什么——切片若无可观察面应显式声明（对照 wish-programming 阶段 3）。
- **边界覆盖最终操作**：小/精确极限、超大单块、多字节文本（字节边界）；分页/滚动/表单校验按 quality-review 证伪刀。
- **测试强度**：断言在目标回归上必失败（负对照）；验证外部状态而非自报；覆盖是必要不充分。
- **实现笔记对齐**：若评审的改动改写了设计决策——设计-spec 备选方案节/决策记录同步了吗？（翻案须新记录+互链，不静默改写）
- **双语/文案**：中英确认包/README 配对一致（本环境约定：与 `dsh-prose-standard` 术语与〔原话〕/〔PM 推断〕标注一致）。

## 报告与接收

- 报告 = 缺陷 + 位置 + 影响 + 证据；局部问题 inline 在最紧 diff 范围，跨切面问题汇总级；blocker 与建议分开。
- 门禁已覆盖的不重复提（绿灯即机器已查）；「一条有据 blocker 优于一串 nit」。
- **接收评审**：逐条验证（跑命令/读代码），技术上有理就修、无理就 rebut；**不表演式同意**（"收到"不算完成，证据才算）。
- 评审会话只读：不越权改实现（诊断请求 ≠ 修改授权，除非用户明说）。
